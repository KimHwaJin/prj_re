# 후속 답변의 근거 ID·수치 분리 성능 비교

설명 요청은 평균 **28.20초 → 10.76초(61.8% 감소)**, 모델 호출 **2 → 1**이었다. 보고서 수정은 변경 후 두 회 모두 성공해 평균 **34.48초**였으며 여전히 모델을 두 번 호출했다. 변경 전 보고서 한 회는 세 번의 수치 정정 실패 뒤 91.72초에 종료됐고, 성공한 한 회는 53.96초였다. 실패를 성공 응답 시간에 섞거나 제외하고 같은 표본 수처럼 비교하지 않는다. 기준은 049까지 포함한 `688a051`이며, 리팩토링 착수 전 전체 코드와의 비교가 아니다.

## 왜 재호출됐는가

실제 거절된 응답을 private 파일로 수집했다. 첫 진단의 설명은 제목 번호·실제 행/열 개수·값의 범위·IQR의 일반적인 비율을 본문에 작성했다. 다음 응답에서도 IQR 비율을 숫자로 쓰며 거절됐고 마지막 응답이 통과했다. 조회나 Worker 대기가 아니라 답변의 수치 분리 규칙 위반이었다.

이 계약에서는 정성 설명은 모델이 쓰고, 실제 값은 성공한 관찰의 selector를 검증한 서버가 표에 넣는다. 숫자를 무조건 허용하거나 삭제해 답변을 통과시키지 않았다. 모델이 본문에 수치를 작성하는 오류는 계속 거절한다.

## 어떻게 바꿨는가

모델이 길고 반복적인 Step/path 객체를 매번 쓰는 대신 짧은 `fact_ids`를 선택하도록 바꿨다. 현재 user/project/session의 source 분석에서만 ID를 해석해 원본 값으로 렌더링한다. 이 목록은 일시적인 모델 문맥이며 데이터 등록 Registry나 Agent 등록 API가 아니다.

원본 관찰은 그대로 보존한다. 모델용 문맥에는 Step별 근거 목록과 실패·잘림·누락 정보를 제공한다. 기존 보고서의 서버 수치 표가 현재 관찰의 표와 완전히 같은 경우에만 중복 표를 제외한다. 모델이 작성한 보고서 해석문은 유지한다. 실제 측정 snapshot의 근거 문맥은 11,130 → 9,577자로 줄었으며 114개 selectable 항목을 포함했다.

prompt만 바꾼 초기 근거 ID 후보에서도 본문 수치 오류가 남았다. 모델에 전달하는 JSON Schema의 `message`와 `fact_ids` 필드에 수치 분리 규칙을 추가 명시한 후보를 최종 측정한다. 기존 create_agent·미들웨어·검증·승인 경계는 유지한다.

## 남은 지연

변경 후 보고서 두 회의 첫 응답은 여전히 본문 수치로 거절됐고 두 번째가 통과했다. 설명에서 첫 응답 통과를 두 번 관찰한 것이 다른 요청의 무정정 응답을 보장하지는 않는다. 수치·owner·source·Step 검증은 유지했다. 다음 성능 후보는 보고서 초안의 해석문과 수치 표현을 더 명확하게 분리해 남은 정정 호출을 줄이는 것이다.

[계측 JSON·실패 포함 원본 숫자](answer-efficiency-2026-10-02.json)에 모든 8회 결과를 기록했다. 초기 prompt-only 근거 ID 실험과 필드 설명 pilot은 이 평균에 포함하지 않았다.

## 최종 측정 조건

- 실제 `qwen38-27b-nvfp4`, temperature 0.2, thinking false. 변경 전·후 각각 설명/보고서 수정 두 회, 총 8회다. 최종 후보를 고정한 후 교차 순서로 순차 실행한다.
- 동일 private 요청·history·완료 분석 snapshot을 사용한다. 설명 입력 SHA256은 `166bf718817df6a506a94175543b5787b0c7e8cffaf0b09e752f573cba58e251`, 보고서 수정은 `bdcc9bee6cc978eb809f6575da9bccce92f0b2a20c3cb96ec08416fb73be7d23`이다. 원문 데이터와 모델 인증 정보는 게시하지 않는다.
- production `create_agent.ainvoke`와 grounding 검증 종료까지 측정한다. 구성/warmup, API/DB/Worker 대기, SSE 전달, Executor 실행은 제외한다. 새 Executor 제출은 없다.
- 공유 모델 자원·다른 환경 부하를 통제하지 못했고 표본도 적다. 중간 실험은 최종 평균에서 제외한다. 같은 입력을 prompt 튜닝에 썼으므로 별도 holdout 품질·부하 검증은 수행하지 않았다.
- 생성된 문장과 선택 항목은 버전·회차마다 다르다. 선택 수와 출력 길이도 함께 기록한다. 처음부터 같은 답변 텍스트를 생성하도록 강제한 순수 계산 성능 비교가 아니다.
- source/Step/실제 값 검증은 자연어 해석의 정답을 보장하지 않는다. 모델의 분포·품질 해석에는 과도한 설명이 남을 수 있다. 이 작업을 새로운 계산이나 의미 검증 기능으로 보지 않는다.

## 재현과 private 진단

```sh
PYTHONPATH=/path/to/revision/src python scripts/benchmarks/conversation/run.py \
  --settings-file /private/path/settings.json \
  --input-file /private/path/fixed-input.json \
  --output /private/path/measurements.json \
  --private-responses-output /private/path/rejected-and-final-responses.json \
  --private-answer-output /private/path/rendered-answer.json \
  --label before --case explanation --iteration 1
```

공통 최종 benchmark 스크립트를 사용하고 PYTHONPATH만 비교할 revision으로 지정할 수 있다. private 옵션 두 개는 선택적이며 원문 파일은 소유자만 읽고 쓸 수 있게 기록한다. 공유·커밋할 결과는 시간/토큰/검증 분류 등 계측 JSON으로 제한한다. 입력 포맷과 측정 범위는 [049 안내](conversation-performance-2026-10-02.md)와 같다.

## 구현 검증과 품질 확인

API·Agent 전체 회귀 908개와 subtest 2개가 통과했다(390.79초). 그 뒤 공용 SessionAnalysisMiddleware에서 분석 업무 import를 없애고 같은 view 함수를 주입받도록 경계를 정리했다. 모델용 문맥과 실제 값 선택은 같으며 최종 관련 84개 회귀와 wheel을 재확인했다. 이 수를 전체 회귀에 더해 세지 않는다. 같은 캐시 Agent의 동시 세션에서도 각자 소유한 값만 출력했고, 새 ID 형식의 Graph 응답·SSE·history가 일치하며 추가 Executor 제출이 없음을 검증했다.

실제 신규 계획 smoke는 32.71초에 등록 Skill 선택 후 data_load/profile_data/compute_statistics/detect_outliers 계획 하나를 검증했다. 신규 계획에는 추가 search_tools 3회가 있었으며 이 요청의 시간 개선은 주장하지 않는다. Executor에는 제출하지 않았다. 최종 설치 package는 source checkout 없이 12개 역할과 prompt, API 36개 path, mock graph 4단계 실행을 확인했다. 공개 OpenAPI의 정규화 hash는 변경 전·후 같았다.

변경 후 네 최종 답변은 본문 수치가 없고 선택한 항목은 모두 기존 근거·실제 값 검증을 통과했다. 보고서의 로드 과정 설명 제외와 통계·이상치·한계 구성도 확인했다. 다만 모델은 결측 비율로 전반적인 품질을 과도하게 평가하거나 분포를 강하게 표현하고, 이전 답변의 근거 footer를 본문에 복제하는 경우가 남았다. 이를 의미 품질 개선이나 통계적 정당성 보장으로 계산하지 않았다.
