## 결론

LLM/그래프가 기다리는 동안 서비스 DB 연결을 점유하던 경로를 제거한 효과는 명확하다. 100명 초기 혼합 부하에서 Run당 Worker 연결 점유가 **94.8%**, 동시에 실행한 CRUD 서버 p95가 **82.7% 감소**했다. 작은 풀에서 취소 감시가 연결을 얻지 못해 실행기가 중단되는 문제도 이전 버전에서 재현됐고 현재 버전에서는 같은 조건을 통과했다.

전체 응답시간이 같은 비율로 빨라진 것은 아니다. 100명 전체 HITL 평균은 **48.41 → 43.35초(10.4% 감소)**였고, 빠른 10명 조건은 일부 지연이 늘었다. 큐 대기·단계별 저장/조회·폴링 비용은 남아 있다.

## 비교 범위와 조건

- 직전 `64ad96f053f538bae798257743945752cb148f38` → 현재 `4bb5c2fc3dcb4475525ff288eab8b0b887b37525`.
- **016 DB 트랜잭션 분리만의 증분 비교**다. 이전 모든 리팩터링을 합친 성능 개선율이 아니다. 두 버전 모두 013 동시 실행·014 공통 소유권·015 종료 처리를 포함한다.
- 총 **80 trial / 20 조건 / 2,852 시나리오 / HTTP 145,563건**. 조건별 before→after 및 after→before의 두 반복.
- 사용자 1·10·30·50·100명 CRUD 단독, 초기 Agent+CRUD 혼합, 전체 4단계 HITL. 추가로 LLM 0.1/5초, 서비스 연결 4/10개, 실행 자리 1개 민감도.
- 기본 단일 프로세스, 실행 자리 4개, 서비스 DB 연결 5개·overflow 0, 별도 checkpoint 풀 최대 4개.
- 실제 FastAPI·HTTP·PostgreSQL queue/Worker·분석 그래프·체크포인트·HITL. LLM Mock, Executor 미제출, 외부 Redis 비활성, Workflow 카탈로그 DB 저장/산출물 제외.
- 상태조회 0.5초, resume 전 사용자 대기 0.2초. 혼합 조건은 별도 초당 20건 CRUD 추가. 장시간 지속 부하가 아닌 독립 burst다.

## 무엇이 문제였고 어떻게 바뀌었나

이전에는 시작 이벤트를 commit한 직후 refresh가 새로운 읽기 transaction을 열었다. 프로젝트 설정 조회·결과 저장도 같은 세션을 사용하면서 모델/그래프 대기 구간까지 연결을 가진 채 넘어갈 수 있었다.

현재는 준비를 commit한 뒤 일반 ID 값만 그래프 경계로 넘긴다. 프로젝트 설정은 짧은 세션에서 읽고 닫으며, 그래프 결과도 별도 짧은 세션에서 저장한 뒤 닫는다. 스트림 역시 저장 세션을 닫고 다음 상태를 기다린다. 기존 공용 풀을 재사용하며, 요청마다 새로운 풀을 만들거나 세션 입력 제한을 해제한 변경이 아니다.

작은 풀의 실제 실패 순서는 **연결 점유 → 취소 감시의 2초 풀 timeout → cancel_watch_failed → 실행 건전성 실패 → 새 Run 점유 중단**이었다. 각 직전 반복에서 running 4개·pending 6개가 남았고 running의 그래프는 실제로 CancelledError로 반환했다. 사용자가 cancel API를 호출한 것은 아니며 정상 HITL interrupt와도 다르다. [오류·DB 상태 증거](data/failure-evidence.json)에 보존했다.

## 남은 지연과 불리한 결과

현재 100명 HITL 평균 43.35초의 근사 분해는 큐 39.20초, Mock LLM 0.40초, 기타 실행 1.17초, 단계별 관찰/HTTP 1.53초, 단계 밖 세션 생성/think time 등 1.05초다. 약 90.4%가 큐 대기다. 큐는 기다린 장소이고, 실행 자리 제한과 각 Run의 실제 처리 비용이 함께 그 대기를 만든다.

빠른 LLM 10명 조건에서는 평균 약 1.01→1.05초, 마지막 완료 약 1.24→1.72초였다. Worker SELECT는 반복당 256→287회로 늘었다. 짧은 세션의 재조회 비용 및 0.5초 폴링 발견 시점이 영향을 주는 양상이며, 모든 증가 시간을 특정 SQL에 귀속시킨 것은 아니다. CRUD 단독 30명 등 일부 대조군도 느려졌고 HTML 표에 모두 표시했다. 두 반복만으로 작은 차이의 통계적 유의성을 주장하지 않는다.

연결 10개에서는 100명 초기 완료 약 55초로 양쪽이 비슷했다. 연결 점유 개선이 모델 시간이나 실행 자리 수를 바꾸지는 않는다는 대조 근거다.

## 검증과 제한

정상 60회는 모두 완료했고 소유권/복구 상태가 정상 반환됐다. 모든 조건 중 미완료는 직전 tight-slow10 두 번의 20건이고, HTTP 오류는 해당 경계 실험의 500 응답 1건이다. HTTP 상태조회가 성공해도 작업 완료를 의미하지 않으므로 최종 상태까지 검사했다.

독립 검증에서 80회/조건별 두 반복/중복 없는 Run·모델 연결/핵심 평균·p95·점유량을 재계산했다. 4,360개 완료 단계 중 3건에서 최대 약 36ms의 음수 시간 잔여가 나왔다. DB transaction 시각·앱 wall clock·monotonic 계측의 경계 차이를 포함하므로 단계 분해는 근사치다. 음수 원본은 삭제·보정하지 않았다. 직접 타이머인 HTTP 및 풀 지표와 구분한다.

Kubernetes 자동 확장, 실제 LLM·Executor·Redis 통합, 일주일 대기, 공유 PV, 지속 부하/메모리 누수, 최대 운영 수용량은 이번 결과로 입증하지 않는다. 기존 환경 설정·서비스를 변경하지 않았으며 전용 측정 DB 컨테이너는 제거했다.
