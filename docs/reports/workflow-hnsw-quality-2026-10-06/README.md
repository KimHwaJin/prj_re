# 095 HNSW Workflow 추천 품질·설정·DB 비용 검증

2026-10-06 / feature/workflow-hnsw-quality / 시작 commit 6ac944a.
[작업 기록](../../improvements/095-workflow-hnsw-quality.md) · [재현 도구](../../../scripts/benchmarks/workflow_retrieval/README.md#095-현재-서비스-검색-구현의-품질비용-대조)

## 판단

094에서 Workflow 3개 중 1개만 찾았던 현상을 동일 벡터 집중 조건에서 재현했다. Workflow 제외 필터를 빼고 직접 ANN을 조회해도 누락됐고, 반환 개수·탐색 폭·스캔·메모리 예산을 늘려도 복구하지 못했다. 같은 데이터에서 인덱스 생성 설정을 바꾸면 결과가 달라졌다. 원인 범위는 **해당 데이터 집중과 HNSW 생성·탐색 구조의 상호작용**으로 좁혔다. 내부 그래프의 모든 연결을 해독하거나 pgvector 구현 버그를 확정한 것은 아니다.

`m=32`는 500개 완전 중복 사례를 해결했지만, 1,000개 완전 중복과 768차원 경계 요청에서 누락했다. **m32 기본값 전환과 조회 예산의 일괄 확대는 권장하지 않는다.** 현재 서비스 설정을 유지한다.

다음 구현 후보는 같은 Workflow·모델 공간·검색 버전에서 완전히 동일한 벡터의 검색 대표를 하나 두는 것이다. 원래 질문과 벡터 이력은 모두 보존하고, 다른 Workflow나 비슷하기만 한 벡터는 합치지 않는다. 이 후보는 아직 구현하지 않았고 일반적인 검색 품질·성능 개선도 입증하지 않았다.

## 검증 범위와 지표

별도 PostgreSQL 17.11/pgvector 0.8.6 컨테이너(53609), CPU 2개·메모리 2GiB, work_mem 4MB에서 시험했다. 실제 `WorkflowSearch`를 직접 호출하고 임베딩 HTTP는 고정 벡터로 대체했다. 검색용 최소 테이블과 2.0 표시의 최소 불변 JSON 파일을 사용했다. 공개 Workflow 전체 스키마·등록 API·인증·Agent 승인·Executor E2E 시험은 아니다. 기존 서비스·DB·Redis·Executor는 변경하지 않았다.

현재 프로필은 ef200, batch64, 최대 8회, scan20000, memory multiplier2, DB+파일 단계 기한 2초다. 내부 후보 한도 20과 화면의 추천+신규 계획 최대 5개는 구분한다. 3개 그룹의 축소 시험만 후보 한도를 3으로 두었다. threshold는 0으로 고정하여 순위를 비교했으므로 운영 기본값 0.93의 적합성은 평가하지 않았다.

| 지표 | 의미와 한계 |
|---|---|
| Recall@5 | 오프라인 전체 벡터의 Workflow별 최소 코사인 거리로 얻은 정답 5개 중, 반환 상위 5개에 포함된 비율. 단순 결과 개수와 다름 |
| 검색 시간 | 실제 함수의 풀 입장·설정·DB·후보 점수 계산·파일 읽기·호스트 왕복 포함. 임베딩 HTTP/LLM/Agent/Executor와 사용자 완료 시간 제외 |
| DB 실행 시간·버퍼 | pg_stat_statements 검색 SELECT 합계. CPU 시간이 아님. 버퍼 hit는 반복 논리 접근이며 물리 페이지 수나 디스크 읽기량이 아님 |
| HNSW 파일 크기 | pg_relation_size. 프로세스 RSS가 아님. corpora의 table_bytes는 인덱스/TOAST를 포함한 pg_total_relation_size |

정확한 전체 검색은 검증 정답에만 사용했다. 서비스 검색에 전량 exact fallback을 넣지 않았다.

## 완전히 같은 벡터 집중

A=[1,.01,0], B=[1,.2,0], C=[1,.4,0], 검색=[1,0,0]인 3차원 대조다. A/B에 각각 50/100/500개, C에 1개를 넣었다. 각 m에서 인덱스를 독립적으로 2회 만들고 요청을 3회 반복했다. 작은 3개 그룹 시험은 Recall@3을 사용한다.

| A/B별 같은 벡터 수 | 현재 m16 | 생성 m32 대조 | 해석 |
|---|---|---|---|
| 50 | 3/3 | 3/3 | 두 설정 모두 이번 표본에서 성공 |
| 100 | 3/3 | 3/3 | 두 설정 모두 이번 표본에서 성공 |
| 500 | 1/3 | 3/3 | m32가 이 축소 조건에는 효과 |
| 500, 동일 벡터를 그룹별 1개로 축약 | 3/3 | 3/3 | 진단 대조군이며 서비스 저장 구조 변경은 아님 |

별도 [직접 SQL 대조](duplicate-probe.json)는 50/100/500/1,000개, 인덱스 생성 전/후 삽입, 그룹 순서/섞인 순서, m16/m32, 5개 조회 프로필을 교차했다. **96번 구축·960번 조회**다. LIMIT5000은 전체 최대 2001행보다 크다. 생성 설정은 pg_class.reloptions로 확인했다.

500개 조건의 m16은 1~2개 그룹만 찾는 경우가 있었고, m32는 이번 12개 인덱스 대조에서 3개를 모두 찾았다. 1,000개에서는 m16은 1개, m32도 1~2개만 찾았다. 필터를 뺀 조회에도 누락됐고, 가까운 그룹을 제외해도 나머지 그룹이 복구되지 않는 경우가 있었다. 입력 순서·생성 시점이나 ef1000/scan100000/memory4만으로 해결되지 않았다.

이는 사내 실제 모델의 한국어 쿼리 결과가 아니다. 3차원 stub이 만든 극단적인 완전 중복 대조다. 실제 임베딩 모델에 이런 집중이 얼마나 존재하는지는 아직 모른다.

## 작은 차이가 있는 768차원 벡터

100 Workflow × 50/500개, 중심 주변에 0.005 노이즈를 주었다. 비활성 Workflow 20/22/24는 partial index에서 제외했다. 같은 seed·벡터·요청으로 m16/m32를 순차 비교했다. 조건마다 독립 인덱스 2회, 집중 요청 4개·경계 요청 4개·각 요청 3회, 조회 프로필 10개다. 표의 셀마다 24개 측정의 평균이다.

| Workflow당 쿼리 | 요청 | 현재 m16 Recall@5 / 평균 | m32 Recall@5 / 평균 |
|---|---|---|---|
| 50 | 집중 | 100% / 41.49ms | 100% / 41.53ms |
| 50 | 경계 | 100% / 49.63ms | 100% / 38.30ms |
| 500 | 집중 | 100% / 73.44ms | 100% / 81.12ms |
| 500 | 경계 | 100% / 79.39ms | 80% / 66.66ms |

m32의 500개 경계 평균 80%는, 4개 요청 중 `boundary-2`가 정답 5개 중 Workflow42 하나만 찾고 나머지는 모두 찾은 결과다. 독립적인 두 인덱스 모두 이 요청에서 누락했다. 정답 순서는 [0,42,2,3,1]이다. **m32의 더 짧은 경계 평균 시간은 성능 개선으로 해석할 수 없다.** 후보를 놓치면 점수 계산과 파일 읽기 비용도 줄어든다.

[추가 경계 대조](boundary-probe.json)는 LIMIT50000, scan1000000, work_mem32MB × multiplier16, ef200/1000, iterative off/strict/relaxed를 비교했다. 필터 없이도 Workflow42의 500개만 찾았고, 42를 제외하면 0개였다. 12개 직접 SQL/EXPLAIN은 HNSW를 사용했다. 따라서 이 관측을 단순한 8회 반복 한도나 작은 LIMIT·기본 스캔 예산만으로 설명할 수 없다. 큰 자원 설정은 운영 권장값이 아니다.

## 조회 설정의 비용

m16·768차원·Workflow당 500개·집중 요청을 비교했다. 모두 이번 표본에서 정답 5개를 찾았다. 후보를 더 많이 확보한 것과 상위 5개 품질의 개선을 구분한다.

| 프로필 | Recall@5 | 평균 | 확보한 내부 후보 평균 |
|---|---|---|---|
| current | 100% | 73.44ms | 8.00 |
| ef500 | 100% | 76.83ms | 8.00 |
| batch256 | 100% | 78.39ms | 8.00 |
| budget_high | 100% | 75.69ms | 8.00 |
| rounds16 | 100% | 202.52ms | 16.25 |

최대 반복 8→16은 73.44→202.52ms, 약 2.76배 시간이 들었다. 이번 표본에서는 상위 5개 품질이 증가하지 않았다. batch256은 50개 조건에서 반복 횟수를 줄여 일부 시간 이득을 보였지만 500개에서는 같은 이득이 없었다. 모든 쿼리 분포의 최적값으로 일반화하지 않는다.

100 Workflow × 500개의 적재+구축 평균은 m16 **33.66초**, m32 **50.55초**였다(각 2회). HNSW 파일은 이 페이지 배치에서 둘 다 189.46MiB였다. m을 늘려도 인덱스·메모리 비용이 항상 같다는 뜻은 아니다. 50개 조건의 적재+구축 평균은 2.31→3.16초였다. 순차 배치·기계 상태·서버의 랜덤 그래프 영향을 분리하지 못해 통계적인 속도 우열을 보장하지 않는다.

## 제한된 동시 요청

각 m에서 24요청 burst를 동시 1/4/10, pool4/overflow0으로 비교했다. [m16 원본](m16/concurrency.json), [m32 원본](m32/concurrency.json)에 모든 요청의 결과를 보존했다. 지속 부하·Pod CPU·API 전체 수용량 시험은 아니다.

m16·동시 4에서:

| 프로필 | 24요청 wall | DB 검색 실행시간 합계 | 공유 버퍼 hit | 평균 Recall@5 |
|---|---|---|---|---|
| current | 537.93ms | 1163.59ms | 1536756 | 100% |
| ef500 | 763.39ms | 1576.17ms | 1662684 | 100% |
| budget_high | 669.57ms | 1745.96ms | 1801341 | 100% |

높은 예산이 이번 burst에서 품질 증가 없이 DB 비용을 더 썼다. 동시 요청의 DB 실행시간 합계는 wall보다 클 수 있다. m32·동시 4 current는 wall644.71ms/DB1661.01ms/평균 Recall90%였다. 품질이 다르므로 이를 동일 품질의 처리량 비교로 해석하지 않는다. 동시 10은 pool4를 유지해 입장 대기가 포함된다. 서비스 Worker·DB 풀 한도를 늘리지 않았다.

## 권장안과 후속

1. **현재 설정 유지:** m16/ef_construction128, 조회 ef200/batch64/rounds8/scan20000/memory2/2초, 내부 후보 20. 실제 모델 정보 없이 m32 전환이나 일괄 확대를 하지 않는다.
2. **완전 중복 벡터 대표화 후보:** 같은 Workflow·모델 공간·search_revision의 완전히 동일한 float32 벡터만 검색 대표 하나로 관리한다. 원래 user_queries와 모든 벡터 이력은 보존한다. 다른 Workflow·근접 벡터를 합치지 않는다. 게시·수정·삭제·승격·복제·재색인 원자성과 500/1,000개 중복·768차원 회귀를 검증해야 한다. 아직 구현하지 않았다.
3. **생성 설정 외부화 검토:** m/ef_construction은 조회 설정과 별개다. 같은 이름의 IF NOT EXISTS는 기존 생성 설정을 바꾸지 않는다. 중앙 설정에 노출하려면 인덱스 정체성·안전한 재구축도 함께 설계해야 한다.
4. **실제 모델 평가:** 주소·모델·차원 제공 후 완전 중복 비율, 현업 정답 쿼리, threshold와 동시 부하를 평가한다. 이번 current100%를 실무 추천 정확도로 일반화하지 않는다.

[pgvector 공식 문서](https://github.com/pgvector/pgvector/blob/v0.8.6/README.md#filtering)는 ANN 필터가 인덱스 탐색 뒤 적용되며 iterative_scan과 예산 조정이 가능하다고 설명한다. [생성 코드](https://github.com/pgvector/pgvector/blob/v0.8.6/src/hnswinsert.c)와 [탐색/이웃 선택 코드](https://github.com/pgvector/pgvector/blob/v0.8.6/src/hnswutils.c)도 참고했다. 특정 그래프의 모든 연결을 해독하지 않았으므로 이 설명만으로 구현 버그를 확정하지 않는다.

## 변경·검증·배포

진단 실행기 3개와 독립 검산기, 원본·요약·설정·실행계획·변경 기록을 추가했다. 기존 실DB smoke의 “전역 첫 후보는 항상 A”라는 단정은 발견 후보 내 점수 정렬 검증으로 수정했다. 모든 후보를 찾으면 전체 정답 순서는 계속 확인한다. 실제 누락은 Recall로 공개하고 테스트 통과로 덮지 않는다.

**현재 검색 구현·공개 API·DB 모델/migration·설정 기본값·Agent 흐름은 변경하지 않았다.** m32와 축약은 진단 DB 대조뿐이며 서비스 소스 SHA 불변도 확인했다.

| 검증 | 결과 |
|---|---|
| [m16 원본 검산](m16/verification.json) | timed1323/인덱스17/계획65/동시9batch, 1543검사 통과 |
| [m32 원본 검산](m32/verification.json) | 같은 규모, 1543검사 통과 |
| [추가 대조 검산](probe-verification.json) | 구축96/조회960/경계12, 1076검사 통과 |
| 실제 PostgreSQL 회귀 | 14 passed, 9.82초. 조회·등록/경합·모델 공간·시간 예산·임베딩 보호 |
| 정적 검사 | 신규 진단 모듈 F 검사, 포맷·compile·diff 확인 |

순차 합계 2646건, 별도 burst432요청이다. EXPLAIN·준비 실행은 timed 결과에 섞지 않았다. **검산 통과는 기록 정합성이며 ANN 품질 전체 합격이 아니다.** 기존 094의 800건을 이번에 다시 실행한 것으로 표시하지 않는다.

초기 진단의 PV 경로를 절대 경로로 잘못 작성해 파일 읽기가 거부된 측정은 중단·수정하고 최종 근거에서 제외했다. 최종 실행기는 비정상 종료를 유효 Recall0 측정으로 받아들이지 않는다. reloptions 중첩 해석도 수정·재검증했다. 093은 corpus와 설정·방법이 달라 이번 결과로 개선률을 계산하지 않는다.

사내 실제 모델·Kubernetes·지속 부하·자연어 평가·추천 계획의 PG 재시작/Executor E2E와 기존 Dataset/Artifact/Gaia/SSO·성능 후속은 남아 있다. 기존 실행 서비스 재기동·머지·푸시·배포는 하지 않았다. 진단 컨테이너와 전용 임시 볼륨만 삭제했다.
