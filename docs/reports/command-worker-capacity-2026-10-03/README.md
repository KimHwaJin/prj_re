# 공통 Worker 소규모 성능 비교 — 2026-10-03

**한 종류에 몰리는 부하에서는 빈 실행 자리 공유로 약2배 처리했고, 사용자/결과가 균형 있게 섞인 경우에는 처리 시간이 거의 같았다.** 개별 graph/LLM 자체가 빨라진 결과는 아니다.

비교 소스는 공통화 직전 `faca5b16c6e2bee559a17b40847414c963af4677`과 정리 완료 현재 `fb35207d2055b9e967ca8792dad971a1fa0bcee2`다. 같은 probe를 두 소스의 git archive에 복사해 별도 Python 프로세스에서 순차 실행했다. Agent/운영 코드는 바꾸지 않았다.

## 완료 시간

독립 세션8개, graph 호출1회당 고정5초, 총 실행 자리4개, 조건별2회 평균이다. 시간은 준비된 queue부터 마지막 DB 완료 상태 확인까지다. 사용자 접수부터 전체 분석 종료까지의 E2E 시간이 아니다.

| 부하 | 이전: 사용자2+결과2 | 현재: 공통4 | 완료 시간 감소 | 처리량 비율 |
|---|---:|---:|---:|---:|
| 사용자 요청만8건 | 20.34초 | 10.34초 | 49.1% | 1.97배 |
| Executor 결과만8건 | 20.32초 | 10.15초 | 50.0% | 2.00배 |
| 사용자4건+결과4건 | 10.20초 | 10.21초 | -0.1% | 1.00배 |

균형 부하의 수십ms 차이는 소규모2회 측정과50ms 완료 관찰에서 의미 있는 개선/악화라고 판정하지 않는다. 단독 부하에서는 이전에 실행 자리가2개 남아 있어도 해당 종류가 쓰지 못했다. 현재는 같은 총한도4개를 모두 사용한다. 균형 부하에서는 이전도2+2로4개를 사용하므로 큰 차이가 날 이유가 없다.

**이전 사용자 한도4와 현재 공통4를 사용자 부하만으로 비교하면 이 자리 공유 효과는 발생하지 않는다.** 기존 설정의 실제 사용자/결과 한도와 도착 비율에 따라 효과가 달라진다. 이번2+2 대4는 총한도를 고정한 구조 비교이며 배포 설정32 등의 확장 성능으로 환산하지 않는다.

## 검증 범위

- 본 측정: 이전6개·현재6개 probe 모두 통과. 총12 sample/96개 job에서 누락·중복 실행·오류0, 완료 후 DB owner/RECOVERY 잔여0. graph 동시 실행 peak는 이전 단독2/혼합4, 현재 모든 조건4다.
- 측정 전 delay0 smoke는 각3개 통과. 측정 도구 검증용으로만 보존하며5초 비교에 섞지 않았다.
- 사용자 경로는 실제 ASGI API로 사전 접수하고 실제 Run claim/준비/취소 감시/소유권/DB 결과 투영을 실행했다. SSO는 기존 테스트 인증 double을 사용하며 HTTP 서버를 띄우지 않았다.
- 이벤트는 실제 Store Inbox ingest/routing으로 사전 준비했다. 이전은 Outbox로 Redis 내부 command를 사전 발행하고 실제 Redis Dispatcher/SessionGuard 및 DB owner 경로를 실행했다. 현재는 DB 공통 명령을 claim해 실제 owner/완료 기록을 실행했다. 외부 원본 Stream 수신 처리량은 비교 범위에 포함하지 않았다.
- graph 작업은 async5초 대기로 대체했다. 사용자 graph 출력은 기존 회귀와 같은 고정 state, 이벤트 graph는 고정 작업이다. 이벤트 업무 결과 투영/checkpoint/보고서/전체 HITL 분석 flow나 실제 Executor/Jupyter/PVC 실행을 수행한 것이 아니다.
- 같은 Python3.11 venv, PostgreSQL17/Redis7 격리 컨테이너, 프로세스1개, CRUD pool8/overflow0와 이벤트 pool8, claim50ms·취소 감시250ms·완료 관찰50ms를 사용했다. 매 조건 queue를 먼저 준비하고 API 연결8개를 warm-up했다. 측정 범위에서 migration·접수·Ingress/routing·Outbox publish·graph 생성·shutdown을 제외했다.
- 실제 PostgreSQL의 완료 상태를 관찰했으며 위pytest 전체 소요 시간에는 migration/setup/cleanup이 들어간다. 이를 표의 처리 시간으로 쓰지 않았다.

## 부가 계측과 제한

| 부하 | 프로세스 CPU 이전→현재 | SQLAlchemy hook 수 이전→현재 | psycopg hook 수 이전→현재 |
|---|---:|---:|---:|
| 사용자 요청만8건 | 1.542→0.972초 | 1049.0→913.0 | 395.0→102.0 |
| Executor 결과만8건 | 2.074→0.672초 | 1130.5→592.5 | 435.0→100.0 |
| 사용자4건+결과4건 | 0.913→0.887초 | 569.0→753.5 | 219.5→101.0 |

CPU는 시험 프로세스만 계측했고 DB/Redis CPU는 포함하지 않았다. SQL은 계측 hook 수이며 주기 routing/metrics·빈 claim·완료 관찰을 포함하고 driver ping 등은 제외한다. 현재는 추가 command 완료 확인이 필요해 관찰 query도 이전과 다르다. 단독 부하에서 실행 시간이 절반으로 줄면 주기 조회 수도 줄어드는 효과가 섞인다. 이 수치를 업무당 DB 비용 절감률이나 NOTIFY 최적화 효과라고 해석하지 않는다.

2회 소규모 burst로 서비스 최대 처리량, 여러 Pod/HPA, 장기 유입 안정성·결과 편향/불공정·큰 원장 이력·접수 트랜잭션 증가 비용을 평가하지 않았다. LLM API 횟수·속도 개선도 없다. 아직 NOTIFY는 구현 전이므로 이번 결과를 신호 최적화의 성과로 설명하지 않는다.

## 판단과 다음 작업

공통화의 성능상 실익은 고정된 총 실행 자리를 부하 비율에 맞춰 쓰는 것이다. 한쪽 집중 시 빈 자리의 낭비가 줄었고, 균형 조건에서 소규모 처리 시간이 크게 악화되지는 않았다. 이 목적에 대한 간단한 확인은 완료했으므로 이번 요청에서 더 큰 테스트를 추가하지 않는다.

다음 구현 우선순위는 기존 계획의 Worker 깨우기 신호/유휴 조회 비용 정리다. 그 뒤 동일 총한도에서1/10/30/50명·실제 분석 흐름·결과 폭주/지속 유입 등을 평가하는 전체 단계5는 별도로 남긴다. 이번 소규모 검사를 전체 단계5 완료로 기록하지 않는다.
