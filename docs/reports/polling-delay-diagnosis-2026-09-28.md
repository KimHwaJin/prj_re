# 상태 조회 간격과 Run 지연 비교 — 2026-09-28

**취소 감시 정체를 제외해도 지연은 남아 있으며, 잦은 상태 조회가 서비스 처리와 대기열 지연을 크게 증폭하는 양상이 확인됐다.** 동일한 정상 워커 4개 구간에서 조회 간격 0.25초→1초 변경 시 Run 평균 대기는 7.19초→3.63초, 워커 처리 시간은 282ms→155ms, 승인 대기까지의 시나리오는 31.0초→17.4초로 줄었다. 다만 이번 실험은 조회 간격에 따라 다음 Run 유입 시점도 바뀌므로, GET 부하만의 독립적인 효과 크기까지 확정한 실험은 아니다.

별도로 0.25초와 1초 조건에서 기존 취소 감시 정체가 각각 1회 재발했다. 2초 조건에서는 이번 5분 동안 정체를 관측하지 못했으며, 이를 재발 방지의 증거로 해석하지 않는다.

**실험 조건과 유지한 상태**

- 로컬 API `127.0.0.1:18080`, PostgreSQL·Redis 로컬, Uvicorn 4개 프로세스와 프로세스당 Run 워커 1개. LLM mock 지연 0ms.
- 각 조건 100명, 초당 10명 증가, 100명 도달 후 준비 구간 30초, 측정 300초. 사용자 생각 시간 0초. 승인 대기 도달 후 즉시 새 세션으로 반복.
- 세션 생성 → data_selection → analysis_context → workflow_candidate_selection → workflow_approval. 한 시나리오에 Run 4개. 승인 응답은 보내지 않아 실제·mock Executor 모두 제출하지 않음.
- 최초 실행과 resume 모두 `POST /api/v1/sessions/{session_id}/runs`. 상태 확인은 `GET /api/v1/sessions/{session_id}/runs/{run_id}`.
- 서버 동작 코드·설정·이미지·컨테이너·프로세스 시작 시각은 유지했다. 기존 진단 계측도 세 조건에 동일하게 유지했다.
- 변경한 것은 Locust와 측정 스크립트뿐이다. 조회 간격 옵션, Run별 제출·관측 시각과 GET 횟수 기록, 실패 시 부분 관측 보존을 추가했다.
- 테스트 간에는 Locust를 정지하고 남은 작업을 기다린 뒤, 증거를 저장하고 해당 시험에서 생성한 정체 Run만 cancel API로 정리했다. 서버 재시작이나 버그 수정은 하지 않았다.

**무엇이 일어나고 있는가**

1. 상태 조회가 실제 자원을 사용한다. 사용자 인증, 세션 소유권, Run 조회에 각각 SELECT가 실행되어 성공 조회 한 번에 3회 DB 읽기가 발생한다. 0.25초 조건의 약 274 GET/초는 이 경로만으로 약 821 SELECT/초에 해당한다. 이는 코드 경로와 요청량으로 계산한 값이며 DB 전체 쿼리 수를 직접 센 값은 아니다.
2. 실행 자리는 4개인데 100명이 다음 Run을 계속 제출한다. 정상 구간의 평균 pending 92.7개 ÷ 완료 12.93 Run/초 ≈ 대기 7.17초로, 실제 측정한 7.19초와 맞는다. 1초 조건도 83.8개 ÷ 22.98 Run/초 ≈ 3.64초로 실제 3.63초와 맞는다. 이 수초의 대기는 한 SQL이나 LLM이 수초 걸린다는 뜻이 아니다.
3. 네 단계에서 같은 대기가 반복된다. 0.25초 조건은 대략 `4 × (대기 7.19초 + 처리 0.28초 + 완료 확인 0.20초) ≈ 30.7초`다. 실제 시나리오 평균 31.0초와 가깝다. LLM 지연이 0이어도 대기열이 전체 사용자 지연을 만들 수 있다.
4. 조회 간격을 늘리면 완료 확인 자체는 늦어진다. 2초 조건의 감지 지연은 단계당 약 1.08초로, 1초 조건의 약 0.53초보다 0.55초 길다. 네 단계에서 약 2.2초 규모의 차이이고, 실제 시나리오 평균 차이는 약 2.6초다. 따라서 GET이 가장 적은 조건이 가장 빠르지는 않았다.

**해석의 한계와 다음 분석**

- 100명이 종료를 확인한 다음 단계로 넘어가는 반복 시나리오다. 조회 간격 변경은 GET 양뿐 아니라 resume/새 Run의 유입률과 분포도 바꾼다. 세 조건을 한 번씩 순서대로 실행했고 데이터는 누적됐으며 Docker 자원도 다른 컨테이너와 공유한다. 따라서 1초가 항상 최적이라거나 GET 감소만으로 정확히 몇 % 개선됐다고 일반화하지 않는다.
- `interrupted` Run의 `completed_at`은 NULL이다. 완료 구간은 DB 상태와 진단 `run_end`를 함께 사용했다. `run_end.outcome=returned`만으로 성공을 판정하지 않았다.
- 워커 반환 전에 최종 DB 상태를 GET으로 읽을 수 있어 단순히 `관측 시각 - run_end`를 계산하면 드물게 음수가 된다. 감지 지연은 커밋 이후 시점인 worker end를 이용한 하한 `max(0, observed-end)`와 커밋 이전 DB `updated_at`을 이용한 상한 `observed-updated_at`으로 보고했다. 이는 정확한 커밋 시각의 점 추정이 아니다. 관련 타임스탬프는 동일 Docker VM의 시계에서 얻는다.
- p95는 원시 관측값의 nearest-rank로 계산했다. 전체 5분 Locust UI의 반올림된 히스토그램 백분위와 조금 다를 수 있다. 완료 시점이 구간 안에 있는 Run/시나리오를 집계했으므로 일부 작업은 준비 구간에서 시작했을 수 있다.

다음 우선 분석은 **Run 유입량을 고정한 상태에서 상태 GET 트래픽만 독립적으로 변화시키는 비교**다. 이를 통해 조회 부하 자체의 영향과 다음 Run 제출 시점 변화의 영향을 분리한다. 그 다음 Graph 생성·결과 저장·checkpoint의 세부 대기를 좁혀 가면 된다. 이번에는 수정안을 적용하거나 서버 병목을 해결한 것으로 간주하지 않는다.
