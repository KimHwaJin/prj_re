# 실제 모델 파라미터·실행·후속 답변 검증

2026-10-04 · `feature/real-model-parameter-validation` · 기준 `354faf8`(087).

실제 `qwen38-27b-nvfp4`와 로컬 Executor/Jupyter로 검증했다. 데이터·컬럼 자동 입력, 사용자 편집의 실제 실행 반영, 결과 이후 방법 선택은 통과했다. 미정 데이터 표현 오류와 보고서 본문 누락을 발견해 수정하고 다시 확인했다. 테스트 수만으로 모델의 이해력·보고서 품질 전체가 보장된다고 해석하지 않는다.

## 발견한 문제와 변경

### 미정 데이터가 null로 채워져 계획 생성 실패

요청: “기초 통계 분석 계획을 만들어줘. 아직 분석할 데이터는 선택하지 않았으니 임의로 고르지 말고, 내가 확인하거나 입력할 수 있게 해줘.”

기존 응답은 `input_values.dataset_id=null`을 포함했다. 이 입력의 schema는 비어 있지 않은 문자열이므로 null은 미정 표시가 아닌 잘못된 실제 값이었다. 앞선 시도에서는 `workflow_input` 참조에 Tool 상수용 `parameter_controls`까지 붙였다. 기존 오류 `Invalid proposed input`은 어느 필드인지 설명하지 않았다. 한 번의 빈 응답·잘못된 참조 정책·null 입력으로 제한된 검증 재시도가 소진됐고 Run이 `recovery_required`로 끝났다. 승인 및 Executor 호출은 없었다.

프롬프트에 미정 키 생략(`input_values={}`), 정상 nullable 함수 인자와의 구분, Workflow input의 편집 선언 위치를 명시했다. 공통 검증 오류에도 필드명과 수정 방법을 추가했다. 잘못된 null을 자동으로 지우거나 dataset을 대신 고르는 로직은 추가하지 않았다.

수정 후 모델은 `required=true`, `has_value=false`인 데이터 선택 폼을 반환했다. 그 상태로 승인하면422였고 interrupt/token이 유지됐다. 이번 응답에도 잘못된 후보 개수의 재시도는 있었다. 이것을 모든 모델 응답이 최초 시도에 정확해진 것으로 해석하지 않는다.

### 보고서를 작성했다고 말하지만 본문 누락

최초 수정 이후 HTTP/근거/추가 실행 여부 검증은 통과했지만 응답을 직접 읽어보니 재작성 요청에 128자의 완료 안내와 서버 근거 표만 반환했다. 재작성된 보고서 본문이 없었다. 따라서 해당 단계의 구조 검사28개 통과를 의미적 전체 성공으로 판단하지 않았다.

대화 프롬프트와 내부 Reply.message 설명에 Markdown 보고서 전문을 응답에 넣고 완료 안내·근거 표만으로 대체하지 않도록 명시했다. 진단에서도 서버 근거 표를 제외한 본문의 제목·내용을 별도로 검사한다. 이 기준은 이 시나리오의 누락을 찾는 진단이며 모든 자연어 응답의 품질 판정기가 아니다.

같은 요청 재검증에서는 제목·통계 해석·한계·다음 질문을 포함한2,036자의 실제 본문을 받았다. 로드 과정 설명을 제외했고 실제 사실 표는 서버가 붙였다. 추가 Executor POST는 없었다. JSON 형식·수치 복제 오류는 기존 제한된 재시도로 수정됐다.

## 실제 실행 결과

| 시나리오 | 확인한 동작 | 결과 |
|---|---|---|
| 명시 데이터·컬럼 | `default-nce`, `columns=["max_val"]` 자동 입력 → 승인 | Executor 통계에 max_val만 포함 |
| 미정 데이터 | 데이터 임의 선택 금지 → 빈 필수 입력 | 미입력 승인422, token 보존 |
| 사용자 편집 | max_val·min_val 제안 → 사용자가 max_val만 남김 | 최종 제출 코드·실제 통계에 max_val만 포함 |
| 결과 이후 판단 | 방법은 deferred → 통계 완료 → 실제 근거로 iqr 선택 | 실제 결과 method=iqr, columns=["max_val"], 후보109개 |
| 완료 결과 설명 | 실제 사실 ID와 source Run 참조 | 새 Executor 제출 없이 답변 |
| 보고서 재작성 | 로드 과정 제외·해석과 한계 강조 | 수정 후 실제 Markdown 본문 반환, 새 제출 없음 |

결과 기반 판단에서 review 역할은 완료된 `load_data`, `statistics`를 받았고 `statistics`를 근거로 선택했다. Agent는 분위수와 최댓값을 참조해 IQR을 선택했으며 그 값으로 `detect_outliers`가 실행됐다. 해당 사유의 통계적 타당성을 일반화하거나 다른 데이터의 최선 방법으로 확정하지 않는다.

편집 사례의 min_val은 사용자가 명시한 값을 보존한 것이며 원본에 존재하는지 사전 검증한 것이 아니다. 실행 전에 사용자가 제거했다. 이번 검증은 임의 컬럼 존재 확인 또는 Dataset Registry 구현의 증거가 아니다.

## 검증 범위와 증거

[비식별 결과 요약](result.json)에 단계별 검사·시간·실제 Executor ID·실패 사실을 기록했다. 첫 수정 후 구조28개, 보고서 수정 재검증11개, 갱신한 API 계약15개를 확인했다. Agent 전체341개와 최종 변경 관련62개 회귀가 통과했고 신규 회귀는2개다. 중복 실행한 테스트 수를 합산하지 않는다. 기존 no-checkpointer durability 경고는 남아 있다.

실제 범위는 HTTP API, SSO 로그인 쿠키/CSRF/Redis 세션, PostgreSQL/Alembic/checkpoint/Store, 두 Worker 역할, Redis Executor 이벤트, Executor/Jupyter, 등록 Tool 원문 제출, 실제 모델·create_agent·middleware다. 직원 확인만 fixture다. 모델 fixture나 초기 계획 fixture는 사용하지 않았다.

임시 API18102·PG53603과 별도 계약 진단18103·PG53604는 실행 후 제거했다. 고유 이벤트 소비 그룹을 사용했고 기존 Compose/업무 DB/원천 Parquet/원래checkout/.env/18100·18101 테스트 서버는 변경하지 않았다. Executor 실행 이력은 남는다. 사내SDK 왕복·실제 브라우저·Phoenix·Artifact 저장·Dataset Registry는 검증하지 않았다.

전체 관측 파일은 `/private/tmp/real-model-parameters-{baseline,after,report-retest}.json`와 `/private/tmp/api-current-contract-088.json`에0600으로 저장했고 repo에는 원문 코드·데이터 샘플·인증정보를 복사하지 않았다. 모델 관측은 JSON middleware handler 경계다. 첫 Skill 선택은 안쪽 middleware가 metadata ToolCall로 변환하므로 원본 gateway 패킷과 동일하다고 표현하지 않는다.

사전 실행이 없는 구조 응답 실패가 `recovery_required`로 분류되어 취소409인 현상은 확인됐다. 현재는 보수적 복구 정책을 유지하고 후속 운영 검토로 남긴다. 프롬프트 개선으로 모든 형태의 모델 실패가 없어졌거나 이 복구 정책까지 해결됐다고 주장하지 않는다.
