# 전체 변경 비교 방법

**최종 실행 범위:** 사용자 요청으로 100명 측정을 중단했다. 완료된 1·10·30·50명 × 초기/현재 = 8개 조건만 본 통계에 포함한다. 현재 1자리 대조와 CRUD 단독 시험은 미실행이다. 아래의 원래 계획과 실제 완료 범위를 구분한다.

비교 기준을 마지막 DB 트랜잭션 변경만으로 잡았던 앞선 보고서를 대체하는 **별도 전체 비교**다. 앞선 DB 전용 측정 결과는 보존하며 합산하지 않는다.

- 초기: 로컬 `feature/total_merge_v1`, `c75182266b14103bed509ddd1ccb5004cd21eb2e`.
- 현재: 애플리케이션 코드 `4bb5c2fc3dcb4475525ff288eab8b0b887b37525`. 그 뒤 `6edaade`는 앞선 시험 스크립트·문서만 추가했다.
- 초기 → 고아 기준 `745a112` 사이에는 기존 `ee66fac`, `dad1d6c`의 Skill/Tool·Workflow 생성 규격 변경과 진단 준비도 포함된다. 이것을 모두 이후 리팩토링 001–016의 성과로 계산하지 않는다.
- 각 commit을 `git archive`로 분리하고, 해당 소스의 API·실행기·그래프·모델 어댑터를 실제로 실행한다. 측정용 wrapper 외 업무 코드는 수정하지 않는다.
- LLM은 별도 로컬 HTTP 서버의 OpenAI 호환 API로 대체한다. 실제 ChatOpenAI와 기존 create_agent 경로를 거쳐 호출하며, **각 모델 응답은 5초** 후 제공한다. 역할별 응답 내용은 고정한다. 추론 품질·토큰 처리량 시험은 아니다.
- 양쪽 모두 `DATA_MOCK=true`의 공통 예제 데이터셋을 선택한다. 업무 데이터 조회·실제 데이터 처리 성능은 범위 밖이다. Workflow/Skill 카탈로그 및 checkpoint 저장은 각 버전의 실제 코드/로컬 DB를 사용한다.
- 분석 흐름은 세션 생성 → 최초 Run → 데이터 선택 → 분석 목적 입력 → Workflow 후보 선택 → 승인 대기. 총 4개 Run과 정상적으로 4개 모델 호출이며 Executor API 호출 직전보다 한 단계 앞인 **Workflow 승인 대기에서 종료**한다. 실제 Executor와 외부 Redis는 호출하지 않는다.
- 동시 사용자 수는 1·10·30·50·100명. 한 배치에 사용자당 하나의 전체 흐름을 동시에 시작하며 무한 재진입은 하지 않는다. HITL 응답 대기는 0.2초, 상태 폴링은 1초다. 실제 사람의 긴 입력 간격을 재현한 일상 트래픽 모델이 아니다.
- 흐름 시험 중에는 별도 고정 20 req/s의 프로젝트 GET/세션 POST를 1:1로 보내 API 영향을 측정한다. CRUD 단독은 사용자당 프로젝트 생성·세션 생성·조회·수정·삭제·프로젝트 삭제를 3회(18요청) 실행하고 회차 간 0.1초 쉰다.
- 한 API/실행기 프로세스. 초기의 실행 자리는 구현상 1개다. 현재 주 비교는 설정으로 4개, 추가 대조군은 1개다. **현재 기본 설정은 1개**이며, 4개 결과를 기본값 그대로의 개선이라고 설명하지 않는다. CPU/RSS·DB 자원 사용 변화도 함께 보고한다.
- PostgreSQL 17 전용 로컬 컨테이너. 매 시험 `identity_test`의 public schema를 초기화하고 각 버전의 CRUD·Worker/Workflow Alembic과 checkpoint setup을 적용한다. 실서비스 DB를 사용하지 않는다.
- API Run Worker만 활성화하고 `EVENT_WORKER_ENABLED=false`, `TASK_RECONCILER_ENABLED=false`를 양쪽에 적용한다. Run 자동 재시도는 0이다. 따라서 Executor 이벤트 처리·Task 만료 점검/복구 정책을 포함한 모든 background 경로의 통합 부하 시험은 아니다. 해당 변경은 기존 개별 검증 근거로 평가한다.
- 실행기 빈 큐 조회 0.05초, 취소 감시 조회 0.25초, Task lease 300초. 현재 감시 기한 6초/정리 기한 3초, 종료 drain 1초/정리 4초는 시험값이며 운영 권장값이 아니다.
- 서비스 풀 10, overflow 0, 연결 대기 5초. checkpoint 풀 min 1/max 4, bridge 풀 4. 풀의 실제 생성·재사용·종료 방식은 버전별 구현을 유지한다.
- 서비스 풀만 동일하게 warm-up한다. 그래프/모델 자원은 첫 호출 시 생성되므로 각 배치 첫 사용자에는 해당 비용이 들어간다. 사용자·기본 프로젝트 준비는 측정 시간에서 제외한다.
- 설정을 명시적으로 주입하고 기존 `.env`를 복사하지 않는다. 초기 Bearer UUID, 현재 X-User-Id 계약을 각각 사용한다. 현재 최초 관리자와 사용자 등록은 사전 준비로 실행한다.
- 그래프·모델·Run 완료·HITL 단계 중 어느 것도 45초간 진전하지 않으면 정체 증거와 미완료를 보존하고 종료한다. 총 기한은 max(90, 사용자 수×25+60)초. 중단된 사용자의 관측 시간은 완료 지연 평균에서 제외하고 censored 수로 따로 표시한다. 미완료를 성공으로 간주하거나 전체 완료시간을 외삽하지 않는다.
- 계측: HTTP 지연/오류, 사용자 전체 시간, Run 큐/실행 시간, 모델 대기, 그래프·풀 생성 횟수, 서비스 DB 연결 점유 초, SQL 시간, event loop 지연, 스레드 수, CPU 초, 프로세스 최대 RSS, 종료 결과. DB 점유 초는 여러 연결의 점유 구간 합이며 벽시계 시간과 다르다.
- 계측 원본을 서버 메모리에 보관하므로 장시간/고빈도 요청일수록 계측 자체의 메모리도 늘어난다. RSS는 관측용 수치이며 제품의 순수 메모리 사용량/누수나 메모리 절감률로 해석하지 않는다. CPU 시간에도 계측 비용이 포함된다. 서로 다른 길이의 시험은 CPU 초/벽시계 초와 요청량도 함께 본다.
- 초기/현재 각 사용자 수의 본 비교는 1배치씩 수행한다. 사용자 p95는 해당 배치의 사용자 분포이며 반복 시험 간 신뢰구간이 아니다. 작은 차이를 확정적 개선/회귀로 해석하지 않는다.
- 정상 흐름 속도 시험은 장애 복구·중복 이벤트·Kubernetes 배포·실제 장기 Executor·공유 PV 검증을 대신하지 않는다. 해당 항목은 기존 검증 기록 및 남은 제한을 연결한다.

## 사전 점검과 본 시험 구분

`smoke`, `smoke2`, `smoke3` 결과는 본 통계에서 제외한다. 계측 wrapper의 인자 충돌, 현재 strict 설정의 레거시 키, Workflow catalog migration 누락을 사전 점검에서 바로잡았다. checkpoint DDL도 요청 전에 준비했다. 사전 점검의 실패를 애플리케이션 성능/장애율로 계산하지 않는다. 최종 smoke는 양쪽 모두 1명 전체 흐름을 통과했다.

## 재현

전용 폐기 가능한 localhost `identity_test` DB에만 `DTEST_BENCH_DATABASE_URL`을 설정한다. 스크립트는 schema를 삭제한다.

```sh
python scripts/benchmarks/total_refactor/run.py --matrix flow --output /tmp/total-refactor-flow
python scripts/benchmarks/total_refactor/run.py --matrix crud --output /tmp/total-refactor-crud
python scripts/benchmarks/total_refactor/run.py --matrix control --labels after --output /tmp/total-refactor-control
```

설정·설명 가능한 결과를 확보한 뒤 본 보고서에 실제 완료/실패 수와 측정 횟수를 기록한다. 개별 기능의 인과 효과는 관련 통제 시험이나 직접 계측이 있을 때만 수치로 귀속한다. 전체 A/B 결과를 16개 변경 각각의 속도 개선율로 임의 배분하지 않는다.

계측 전송 보완: 30명 초기 시험 진행 중, 이후 서버들의 `/_bench/metrics` 응답을 같은 내용의 JSONResponse로 바꿨다. 많은 원본을 측정 종료 후 내보낼 때 FastAPI가 중복 변환하는 비용을 피하기 위한 것으로 업무 실행·측정 구간·계측 항목은 바꾸지 않았다.

혼합 CRUD의 추가 해석 제한: 20 req/s를 시험 종료까지 계속 보내므로 오래 걸리는 초기 조건에는 새로 만들어진 세션과 총 요청도 더 많다. 양쪽은 같은 초기 상태와 유입 규칙이지만 끝의 데이터 양은 같지 않다. 혼합 API 지연 차이를 DB transaction 변경 하나의 순수 효과로 분리하지 않으며, 동일 요청 수 CRUD 단독과 현재 1자리 대조를 함께 본다.
