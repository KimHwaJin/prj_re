# 처음부터 현재까지: 무엇을 바꿨고 무엇에 영향을 주는가

실제 부하 결과는 완료된 1·10·30·50명 비교다. 100명은 사용자 요청으로 중단했고, 현재 1자리 대조 및 CRUD 단독 시험은 미실시다.

이 문서는 전체 시간 수치만으로 설명되지 않는 변경을 연결한다. 실제 성능 수치는 같은 폴더의 최종 보고서·원본을 기준으로 한다. 기존 기능 검증 기록은 이번 부하시험에서 새로 실행한 시험과 구분한다.

## 비교 범위의 정확한 경계

사용자가 지목한 출발점은 `feature/total_merge_v1`의 `c751822`다. 고아 리팩토링 브랜치 최초 commit `745a112`와는 다르다. 그 사이 `ee66fac`, `dad1d6c`에서 이미 Skill/Tool 목록과 Workflow 생성 규격 등을 바꾸었다. 이번 전체 A/B는 그 변경도 포함한다. 따라서 파일 삭제량이나 전체 속도 차이를 모두 리팩토링 001–016의 독립 성과로 합산할 수 없다.

초기 → 고아 기준: src 기준 46개 파일, +653/-4,022줄. 고아 기준 → 현재: src 기준 243개 파일, +8,021/-4,290줄. 두 구간은 중복 파일을 포함하고 rename 판정도 있으므로 파일 수·줄 수를 단순 합산하거나 품질 점수로 해석하지 않는다.

## 1. 큰 다중 사용자 시간 차이를 만드는 변경: 실행 자리

**이전:** Worker가 한 Run을 점유하고 `await execute_claimed(...)`가 반환된 뒤 다음 Run을 점유했다. 한 사용자 전체 대화 동안 계속 독점하는 것은 아니지만, 초기 호출 또는 resume 한 번의 그래프 실행이 진행되는 동안 다른 Run을 실행하지 않았다. 두 번의 5초 모델 호출을 포함하는 단계라면 그동안 다른 세션은 순서를 기다린다.

**현재:** 같은 프로세스에서 설정한 개수만큼 서로 다른 세션의 Run을 함께 실행한다. DB의 SKIP LOCKED는 여러 실행자가 같은 Run을 중복 점유하지 않게 하고, `AGENT_WORKER_CONCURRENCY`는 프로세스 내부 동시 실행 수를 제한한다. 두 기능은 다른 책임이다.

**영향:** 줄어드는 핵심은 LLM 자체의 5초가 아니라 큐 대기다. LLM 대기 중 빈 CPU 시간을 다른 세션에 사용한다. 프로세스/Pod를 추가하지 않아도 여러 LLM 요청이 동시에 진행될 수 있다. 다만 모델 공급자가 그 동시 요청을 감당해야 한다. 이번 Mock은 동시 처리 한도가 없는 고정 지연이므로 실제 공급자 처리량을 입증하지 않는다.

**중요한 설정 차이:** 기본값은 여전히 1이다. 4자리 성과는 코드가 제공하는 동시 실행 기능에 설정값 4를 적용한 결과다. 같은 1자리 추가 대조가 있어야 코드 교체만의 효과를 더 분리할 수 있다. 이번에는 사용자 요청으로 해당 대조 전에 보고를 마쳤다.

같은 세션은 실행 중 입력을 허용하지 않는다. HITL에서는 해당 응답만 허용하고, Executor 대기에서는 새 사용자 입력·사용자 resume를 막는다. 다른 세션은 독립 실행 가능하다. 새 `WAITING_EXECUTOR` DB enum을 만들었다는 뜻이 아니라 기존 Task 상태와 interrupt 종류로 구분한다.

근거: [013 기록](../../improvements/013-run-concurrency.md), `src/app/agent_run_worker.py`, `src/app/services/run_service.py`.

## 2. DB 연결 점유를 줄이는 변경: 짧은 transaction

**이전:** 그래프 실행에 들어가기 전에 읽은 SQLAlchemy Session의 transaction이 열린 상태로 유지될 수 있었다. LLM 응답을 기다리는 동안 DB 작업이 없어도 서비스 DB 연결은 다른 요청이 사용할 수 없었다.

**현재:** 입력·식별값을 읽고 연결을 반환한 다음 그래프를 실행한다. 메시지/상태를 저장할 때 짧은 session을 다시 사용한다. Checkpoint와 bridge용 기존 풀은 별도이며 이 변경이 모든 DB 연결을 하나의 풀로 합친 것은 아니다.

**영향:** 한 사용자의 LLM은 빨라지지 않는다. 대신 많은 Run이 모델을 기다려도 CRUD/상태 API가 빌릴 수 있는 연결이 남는다. 이전의 016만 비교한 시험은 이 효과의 별도 근거이며, 이번 전체 A/B는 초기 구현 대비 결과다. 두 시험의 개선율을 더하지 않는다.

총 DB 점유 초에는 background CRUD와 폴링도 포함된다. 초기 코드가 더 오래 실행되면 그 요청 수도 더 많다. 따라서 **Worker 점유 초/Run**과 API 지연을 우선 보고, 서로 길이가 다른 시험의 전체 점유 초 감소를 그대로 독립 효율 개선율로 해석하지 않는다.

근거: [016 기록](../../improvements/016-short-db-transactions.md), [이전 변경 단독 비교](../db-scope-comparison-2026-09-29/report.md).

## 3. 반복 생성 비용을 줄이는 변경: 자원 수명

**이전:** 최초 호출과 각 resume가 그래프·checkpoint 풀·bridge 풀을 새로 구성하고 종료했다. 이번 4 Run 사용자 흐름에서는 그래프 4회, psycopg 풀 8회가 생성됐다.

**현재:** 프로세스의 런타임이 그래프와 풀을 소유하고 각 Run은 빌려 쓴다. 같은 런타임의 다른 세션도 같은 구성을 사용하고, session/thread 식별자로 상태를 분리한다. HITL 때 사용자를 기다리며 DB 연결을 계속 checkout하는 구조가 아니다.

**영향:** 재구성·연결 수립을 줄인다. 한 번의 5초 모델 추론에 비해 짧은 비용이므로 1명 전체 응답시간이 수 배 빨라질 이유는 없다. 장시간/반복 호출에서 자원 생성 횟수가 늘지 않는 것이 직접적인 성과다. 풀 생성 누적 횟수는 동시 연결 개수가 아니다. 풀 상한과 실제 열린 연결 수는 다르며, 프로세스/Pod가 증가하면 풀도 증가한다.

API와 Executor 이벤트 런타임 사이의 모든 풀까지 통합한 것은 아니다. 모델 HTTP client의 종료 관리, 비풀 Workflow DB 접근 등은 별도 검토 대상이다. 코드/프롬프트 초기 구성을 재사용하므로 변경 반영에는 프로세스 재시작이 필요하다.

근거: [004 기록](../../improvements/004-graph-resource-lifecycle.md).

## 4. 동기 호출 → 비동기 호출이 바꾸는 것

**이전:** 모델 `.invoke()`가 사용됐다. 하지만 외부 graph는 `ainvoke()`로 실행됐고, LangGraph가 동기 노드를 executor 스레드에서 실행했다. 따라서 '모든 LLM 대기가 FastAPI 이벤트 루프를 5초씩 막았다'고 설명하면 틀리다. 이번 계측에서도 이전 모델 호출은 `asyncio_*` 스레드, 현재 호출은 async `MainThread`로 구분된다.

**현재:** 역할별 모델 호출은 `create_agent` → `ainvoke()`로 동작한다. 네이티브 비동기 전송을 사용해 모델을 기다리는 동안 스레드를 붙잡지 않는다. 동기 파일/기존 HTTP/DB 작업은 `run_sync` 등의 관리 경계에서 실제 종료를 확인한다.

**영향:** 이 변경 단독으로 공급자의 응답 5초가 짧아지는 것은 아니다. 동시 실행의 자원 효율과 취소 전파를 개선하는 기반이다. 실행기 자체가 1자리이면 여러 요청을 실행하지 못하는 문제는 남는다. 모든 파일/HTTP/DB I/O가 native async로 전환된 것도 아니다.

근거: [006 기록](../../improvements/006-agent-async-llm.md), [012 기록](../../improvements/012-agent-flow-validation.md).

## 5. 멈춤·중복 실행·재배포는 정상 응답시간과 다른 성과

- **001 cleanup:** 정상 완료에는 감시 task의 cancel 대신 stop event를 전달하고 DB 감시·정리에 기한을 둔다. 종료가 불확실하면 `recovery_required`, 건전성 실패, 소유권 보존으로 추가 실행을 막는다. 기존 통제된 경합 시험의 수정 전 20/20 정체 → 수정 후 0/20은 별도 장애 주입 결과다. 이번 정상 부하에서 같은 비율로 발생한다는 의미가 아니다.
- **014 공통 소유권:** `session_executions`의 토큰을 API Run과 Executor 이벤트가 공통으로 사용한다. 짧은 transaction으로 점유/갱신하고 그래프 대기 동안 행 lock을 유지하지 않는다. 오래된 heartbeat만 보고 다른 실행자가 토큰을 빼앗지 않는다. 이전에는 양쪽 보호 저장소/경계가 달랐다.
- **015 종료:** 새 점유 중단 → 진행 중 호출의 정상 완료 유예 → 남은 호출 취소/정리 확인 순서로 바꿨다. 일주일 걸리는 외부 Executor가 끝날 때까지 Pod를 붙잡는 기능이 아니다. 해당 호출이 interrupt로 반환하고 checkpoint/상태 저장이 끝나면 실행 자리는 반환한다.

**비용과 미완료:** 안전 확인을 위한 SQL/상태 처리가 추가되므로 정상 무부하 경로가 무조건 짧아지지는 않는다. 종료가 불확실한 세션은 자동 재시작하지 않는다. 관리자 복구 API, checkpoint 쓰기 세대 차단, 강제 종료/네트워크 단절 후 자동 인계는 아직 남아 있다. 이전 Worker와 새 Worker의 혼합 배포도 별도 전환 절차가 필요하다.

근거: [001](../../improvements/001-run-cleanup-stall.md), [014](../../improvements/014-session-execution-ownership.md), [015](../../improvements/015-graceful-shutdown.md). 실제 SIGTERM/DB 경합 검증은 각 작업 당시 기록이며 이번 정상 부하 시험에서 전체 재실행한 것이 아니다.

## 7. 이 비교로 결정할 수 있는 것과 없는 것

이 비교는 한 프로세스의 서비스 구조가 동일한 5초 모델 대기를 처리하는 능력, API에 미치는 영향, 반복 자원 생성을 보여준다. 최소 Replica 운영에 유용한 근거지만 특정 운영 슬롯 수를 보증하지 않는다. 실제 모델 동시 처리량과 모든 서비스의 DB 연결 총량을 함께 맞춰야 한다. Pod별 풀 상한은 자동으로 늘어나는 모든 Pod의 DB 연결 총량 상한이 아니다.

본 시험에서는 실제 Executor 제출·Redis 이벤트·1주 대기·공유 PV·Kubernetes scale-in/out을 실행하지 않는다. 이벤트/종료 개선의 기능 근거는 기존 개별 검증으로 연결하고, 이 부하 결과를 장기 운영 검증으로 확대하지 않는다. '전체 변경 비교'는 지금까지 구현한 변경 전체가 비교 대상이라는 뜻이며 전체 설계의 모든 기능이 완료됐다는 뜻은 아니다.

합의된 전체 API 정리도 모두 끝난 것은 아니다. 이번 실제 흐름은 최초 호출/resume마다 별도 Run을 만들어 사용자당 4개 Run이 생긴다. 전체 논리 작업의 공개 run_id 통합, Message CUD/Tasks 공개 API 정리 등은 완료된 변경으로 계산하지 않는다.

예를 들어 `src/app/services/project_service.py`의 read는 현재도 하위 Session 목록과 message_count 집계를 함께 읽는다. 이 파일은 초기/현재 비교에서 바뀌지 않았다. 기본 CRUD 전체가 가벼운 단건 조회로 재설계됐다고 설명하지 않는다.
