# 결과 저장 DB 왕복 축소 — 033 성능 검증

정상 결과 저장의 Worker SQL은 사용자당 **344회에서 281회(18.3% 감소)**로 줄었다. 결과 저장 구간도 두 조건에서 짧아졌다. 그러나 **10명 조건 전체 응답과 배치 처리량은 사실상 동일**하다. 이번은 저장 비용을 줄인 1차 개선이며 전체 시스템 성능 최적화 완료를 의미하지 않는다.

## 기준과 변경

- 변경 전: `8836df6` (032 완료).
- 변경 후 측정: Git tree `88e026542f7fd2dc8251cc5344a5e29c1919e7e5`. 이 스냅샷의 변경 운영 파일 4개가 최종 033 소스와 byte 단위로 일치함을 확인했다. 최종 commit에는 테스트·문서·측정 도구가 추가된다.
- [운영 코드 차이](production-diff.patch): INSERT RETURNING 재사용, 메시지 lifecycle 잠금 결과 재사용, 반환 DTO 생성 후 commit, 동일 Task 연결 no-op. Worker 수·동시성·모델 호출·Agent 업무 순서·DB schema는 동일하다.
- API 1프로세스, 동시 실행 4개, 서비스 pool 10/overflow 0, checkpoint 1–4, bridge 4, 로컬 PostgreSQL 17, 모델 HTTP mock 5초/호출, 사용자당 4회 호출. SSE·단계 간 0.2초 생각 시간. 세션 생성부터 resume 3회 및 Workflow 승인 대기까지 측정한다.
- 1·10명 조건을 before→after→before→after 순서로 각각 2회 측정했다. 각 trial마다 DB 초기화 및 프로세스/풀 재시작을 수행했으므로 초기화 비용이 포함된다. 사용자 생성은 측정 밖, 세션 생성은 측정 안이다.
- 8개 trial, 44명, 176개 실행 구간/모델 호출 모두 정상. 실패·재시도·복구 필요·점유 누수·강제 kill 없음. 종료 SIGTERM의 정상 관측 return code는 0 또는 -15로 구분했다.

## 시간 결과

사용자 한 명의 전체 흐름 평균이며 두 반복을 동일 가중 평균했다. 내부 처리에는 저장 구간이 포함되므로 두 열을 더하지 않는다. 저장 구간은 persistence.* span이며 최종 Run 상태 저장·API 접수 등 전체 DB 작업의 합이 아니다.

| 동시 시작 사용자 | 전체 평균 전→후 | 큐 대기 전→후 | LLM 전→후 | 내부 처리 전→후 | 결과 저장 전→후 |
|---|---:|---:|---:|---:|---:|
| 1 | 24.534 → 24.229초 | 0.922 → 0.853초 | 20.078 → 20.074초 | 1.486 → 1.274초 | 0.592 → 0.429초 |
| 10 | 48.220 → 48.179초 | 25.162 → 25.103초 | 20.028 → 20.027초 | 1.036 → 0.965초 | 0.488 → 0.415초 |

결과 저장 시간 감소는 1명 27.6%, 10명 14.9%로 관측됐다. 전체 시간은 각각 약 1.25%, 0.09% 차이다. 두 반복과 로컬 환경만으로 전체 응답 개선의 통계적 유의성이나 운영 SLA 향상을 주장하지 않는다.

| 사용자 | 배치 처리율 전→후 (완료 사용자/초) | 의미 |
|---|---:|---|
| 1 | 0.0408 → 0.0413 | 고정 동시성·5초 모델의 동시 시작 배치 |
| 10 | 0.1799 → 0.1799 | 고정 동시성·5초 모델의 동시 시작 배치 |

배치 처리율은 각 반복의 완료 사용자 합/배치 완료시간 합이다. 평균 사용자 응답시간의 역수나 요청 RPS가 아니다. 특히 10명 조건은 약 0.180명/초로 사실상 같아서 이번 변경으로 최대 처리량이 늘었다고 결론 내릴 수 없다.

## DB 작업 감소

전체 흐름에서 Worker의 서비스 SQL은 모든 trial에서 사용자당 344→281회다. AsyncSession.commit **호출**은 51→48회다. 이 수치를 checkpoint/bridge SQL이나 실제 wire COMMIT 횟수로 해석하지 않는다. 아래 독립 probe는 SQLAlchemy cursor 실행과 engine transaction commit을 직접 계측했다.

| 저장 작업 | SQL 실행 전→후 | 실제 DB commit 전→후 |
|---|---:|---:|
| 새 로그+이벤트 | 8→5 | 1→1 |
| 기존 완성 로그 | 1→1 | 0→0 |
| 새 메시지 | 11→9 | 1→1 |
| 기존 메시지 | 8→7 | 0→0 |
| 새 Task 연결 | 3→2 | 1→1 |
| 이미 같은 Task 연결 | 2→1 | 1→0 |

[이전 SQL 증거](before-queries.json), [이후 SQL 증거](after-queries.json). 쿼리 파라미터/실사용자 데이터는 저장하지 않았다. 신규 메시지의 ID/sequence/DB 생성 시각·세션 leaf, 중복 저장·동시 요청 결과, graph task 충돌 보호가 유지되는지 검증했다.

## 해석과 남은 성능 항목

10명에서는 사용자당 LLM 약 20초와 큐 약 25초가 대부분이다. 전체 내부 처리 약 1초 중 일부를 줄였으므로 사용자 체감 지연이나 처리량의 큰 변화가 나오지 않은 결과와 일치한다. 저장 왕복 감소는 명확하지만 실제 DB가 원격일 때의 효과, 더 큰 처리량, 최적 동시성 값은 이번 데이터로 확정하지 않는다.

메시지별 권한·세션 확인과 로그/이벤트별 저장·commit은 여전히 남아 있다. 다음 성능 개선 후보는 한 결과 반영 구간의 반복 검증 공유 및 저장 단위 묶기다. 이를 전부 불필요한 SQL로 단정하지 않고 순서·멱등성·잠금 범위를 보존하면서 검토해야 한다. 실행 동시성별 처리량/자원 한도 검증도 남아 있다. 모델 호출 수·병렬화·실행 단위 변경은 새 Agent 흐름 검토와 함께 다룬다. 신규 장애 대응·운영성 작업은 사용자 우선순위대로 마지막 단계로 미룬다.
