# 069 서비스 CPU 진단·워커 조회문 재사용

상태: 독립 기준 소스에서 구현·실제 PG 회귀·동일 조건 측정 완료 / 베이스 미병합·미푸시·미배포.
브랜치: `feature/service-cpu-profiling`.
비교 기준 `f2009d1`, 구현 `2a815c8`. 065 전체 값 저장에 검증된068 이력 경로 수정만 반영했다. 보류된066 증가분 저장 후보는 포함하지 않았다.

기존 문제는 공통 Worker가 작업을 찾을 때마다 동일한 ORM alias/복합 SELECT/캐시 키 구조를 새로 만드는 CPU 비용이다. 메인·offload thread CPU 진단에서는 SQLAlchemy 처리 비용이 큰 비중이었다. 이 전체 비용을 claim 조회문 한 곳 때문이라고 단정하지 않는다.

변경은 `runs/commands/claim.py` 한 곳이다. 불변 SQL 구조만 한 번 선언하고 namespace·현재 시각은 호출마다 새로 바인딩한다. DB 결과/Run/소유권/session은 캐시하지 않는다. 매번 DB 조회·FOR UPDATE SKIP LOCKED·동일 세션 선행 명령/활성 Task/Owner 조건과 commit을 수행한다. 모델/승인/이벤트 순서/포맷/durability/풀/한도는 동일하다.

LLM0·HTTP Executor 합성 출력 조건에서1/10/30명 각 전후1회, 50명 각3회(총12회·382흐름)를 측정했다. 전체 완료 시간은1명1.716→1.691초,10명4.471→4.450초,30명13.350→12.764초,50명 평균21.884→21.200초다. 50명 서비스 CPU는21.142→20.471초(3.2% 감소)였다. 10명 CPU는0.6% 증가했다. 큰 개선이나 안정적인 운영 처리량 확보로 표현하지 않는다.

진단·overhead 시험을 포함한 전체19회·416흐름에서 오류0, 실제 PG 회귀17개(skip0), 원본/SHA/소스/집계 독립 검산1,200개를 확인했다. profiler on은 표준10명 시간을 약2배로 늘려 성능 수치에서 제외했다. 측정용 자원만 정리하고 기존18개 서비스·원래 checkout/.env를 보존했다.

다음 성능 후보는 PublicRunService 상태 snapshot 조회문의 반복 구성 비용이다. 이번 성과와 합산하지 않는다. 실제 Pod 자원·지속 부하·전체 replica DB 연결 예산, 기존066 혼합 버전 비호환·067 최초 중단 원인은 남아 있다. 모델 호출 수/Registry/Workflow CRUD/광범위 운영 보완의 보류는 유지한다.
