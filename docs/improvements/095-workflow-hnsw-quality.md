## 문제와 판단

094의 동일 벡터 500개 집중에서 3개 중 1개만 발견한 현상을 재현했다. 필터 없는 직접 SQL에서도 누락했으며 조회 예산을 늘려도 해결되지 않았다. m32는 500개 완전 중복에 효과가 있었지만 1,000개와 768차원 경계 요청에서는 누락했다. 특정 생성·집중 조건에 민감한 ANN 누락으로 범위를 좁혔으며 내부 그래프의 모든 연결이나 구현 버그를 확정하지 않았다.

현재 m16/ef128과 조회 ef200/batch64/rounds8/scan20000/memory2/2초/내부 후보20을 유지한다. m32 일괄 전환이나 조회 한도 확대는 권장하지 않는다. 같은 Workflow·모델 공간·검색 버전에서 완전히 동일한 벡터의 검색 대표화가 다음 구현 후보다. 모든 질문과 벡터 이력을 보존하며 다른 Workflow나 비슷한 벡터는 합치지 않는다. 이 구조는 아직 구현하지 않았다.

## 실제 변경

현재 WorkflowSearch를 직접 호출하는 진단 실행기, 삽입·생성 순서/설정 대조, 경계 실패 읽기 전용 조사와 독립 검산기를 추가했다. 원본·요약·지문·권장안·한계를 기록했다. 기존 실DB smoke에서 전역 최상위를 항상 반환한다는 단정은 후보 내 정렬 계약으로 바로잡았다. 모든 후보를 찾으면 전체 정답 순서는 계속 확인한다.

서비스 검색·Agent·공개 API·DB 모델/migration·운영 설정과 기본값은 변경하지 않았다. m32와 축약은 진단 대조만이며 서비스 소스 SHA는 동일하다.

## 검증

- 순차2646측정/130EXPLAIN, 별도432burst요청, 추가구축96/조회960/경계12를 완료했다.
- 독립 검산1543×2+1076=4162 통과. 이는 기록 정합성이며 ANN 품질 전체 합격은 아니다.
- m16은 이번768차원 상위5개를 찾았지만, m32의500개 경계 평균Recall은80%였다. m16 집중500개에서 rounds8→16은73.44→202.52ms로 비용만 늘었다.
- 실제DB 회귀14 passed(9.82초), 신규 진단 F/포맷·compile·diff 및 저장 지문을 검증했다. 기존094의800건을 이번 재실행으로 표시하지 않는다.

실제 임베딩·자연어 정확도·종합 성능/SLA는 검증하지 않았다. 초기 PV 경로 오류 측정과 reloptions 검산 해석 오류는 수정·재검증했으며 최종 근거와 구분한다.

## 다음과 배포

완전 중복 벡터 대표화의 원자적 색인·보존·회귀 계약과 실제 모델 평가는 후속이다. 필요하면 인덱스 생성 설정 외부화와 안전한 재구축도 함께 설계한다. 근접 벡터 요약은 추가 품질 검증 없이 도입하지 않는다.

현재 서비스·Executor·Redis를 재기동하지 않았다. 진단 컨테이너와 전용 임시 볼륨만 삭제했다. 파생 브랜치에 커밋하며 머지·원격 push·배포는 진행하지 않는다.
