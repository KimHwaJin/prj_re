## 문제와 작업 범위

접수 제한/과부하 정책을 진행하기 전에 내부에서 소요하는 시간이 충분히 정리됐는지 근거가 필요했다. 이번에는 초기 코드와 현재를 비교하지 않고 현재 흐름을 접수·큐·LLM·DB 반영·checkpoint·결과 수신으로 분해했다. 운영 설정과 API/Agent 코드는 수정하지 않았다.

[상세 보고서](../reports/runtime-latency-profile-2026-09-29/report.html), [정의·재현 절차](../reports/runtime-latency-profile-2026-09-29/README.md), [집계 원본](../reports/runtime-latency-profile-2026-09-29/summary.json).

## 조건

API 프로세스 1개, Run 동시성 4, 로컬 PostgreSQL 17, LLM HTTP mock 호출당 5초, 사용자당 4회 모델 호출. 동일 사용자의 세션 생성 → agent 호출 → resume 3회 → Workflow 승인 대기에서 종료한다. 단계별 모델 호출은 2/0/2/0회다. SSE로 상태를 받고 단계 사이 0.2초 생각 시간을 둔다. Executor·Redis·100명 조건은 제외했다. 서비스 기본 동시성 1은 변경하지 않았다.

서비스 DB pool 10/overflow 0, checkpoint pool 1~4, bridge pool 4, Worker/cancel poll 0.25초, SSE coalescing 기본 0.5초. 계측은 별도 wrapper에서 수행했다. 실행 소스는 git archive로 고정하고 `.env`는 로딩하지 않는다. 각 배치는 연결 풀을 준비한 새 프로세스로 실행하며 그래프 최초 로딩은 측정에 포함했다.

## 결과

각 수치는 사용자 한 명의 전체 흐름 평균(초)이다. 전체 = 큐 + LLM + 내부 + 구간 밖 잔여. 반올림 오차가 있을 수 있다.

|---|---:|---:|---:|---:|---:|
| 1 | 23.96 | 0.57 | 20.07 | 1.52 | 1.81 |
| 10 | 48.15 | 25.11 | 20.03 | 1.06 | 1.94 |
| 30 | 151.00 | 127.82 | 20.02 | 0.92 | 2.23 |
| 50 | 257.65 | 234.20 | 20.03 | 1.05 | 2.37 |

- 91명/364개 실행 구간/364회 모델 호출 정상. 재시도·복구 필요·세션 점유 누수·강제 종료 없음. 승인 대기까지 진행하므로 DB 실행 구간의 interrupted는 정상이다.
- 50명 조건의 슬롯 점유율 97.17%. CPU 사용률이 아니라 Worker가 실행 자리를 점유한 시간의 비율이다.
- 50명 조건의 LLM 없는 두 번째 단계: 처리 0.1505초, 큐 대기 60.0300초. 마지막 단계: 처리 0.2451초, 큐 대기 54.4680초. 짧은 재개도 긴 작업과 실행 자리를 공유한다.
- DB 반영 구간은 0.5205~0.6992초/사용자. Worker의 서비스 SQL 322회/사용자, commit 호출 61회/사용자. psycopg checkpoint·bridge SQL과 실제 COMMIT 수로 해석하지 않는다.
- 50명 DB pool 획득 P95 1.705ms, 최대 772.916ms. 100ms 초과 201건 중 200건이 첫 2초에 발생했다. 순간 접수 경합은 남았지만 긴 대기 전체를 설명하지 않는다.
- 최종 커밋 이후 SSE 관측까지 네 단계 합계 1.1433~1.4150초/사용자. 전체 시간에 이미 포함되어 있으며 순수 서버 처리 시간이나 coalescing 설정만의 효과가 아니다.
- 그래프 생성은 배치당 1회. 공유 psycopg 풀 생성도 배치당 bridge/checkpoint 각 1회. 최초 초기화 비용이 사용자 수로 분산되는 것을 코드 개선 효과로 해석하지 않는다.
- 모든 모델 호출은 async, 모델 HTTP는 non-streaming. 따라서 027 토큰 저장 버퍼의 성능 효과는 이번 시나리오로 검증하지 않았다.

## 판단과 다음 방향

수십~수백 초의 주요 원인은 실행 슬롯 경쟁이다. 내부 처리의 측정 평균은 약 1초이며, 내부 코드를 전부 최적화하면 큐가 사라진다고 볼 수 없다. 동시에 내부 개선 완료라고 선언할 근거도 없다.

다음 내부 개선 후보는 `graph_crud_persistence`/`AgentRunLogService`/`TaskEventService`의 개별 저장·반복 조회·commit/refresh다. 로그와 durable event의 원자성·멱등성·순서를 보존하면서 왕복을 줄일 수 있는지 검토한 뒤 같은 조건으로 A/B한다. 아직 구현하거나 절감 효과를 측정하지 않았으므로 SQL 322회 전체를 불필요하다고 표시하지 않는다.

SSE 변경 전달 지연, 짧은 resume의 큐 대기 정책, 동시성 적정값은 별도 문제로 검토한다. 접수 제한은 처리 시간을 줄이는 기능이 아니므로 이번 내부 개선을 대신하는 항목으로 진행하지 않았다.

## 실제 변경과 검증

- `scripts/benchmarks/runtime_profile/`: 현재 버전 전용 실행 harness, 메모리 계측 wrapper, 겹침 제거 집계, 별도 검산, 보고서 생성.
- 1/10/30/50명 실제 HTTP·SSE·PostgreSQL·LangGraph 흐름 및 SQL/진단 span 계측. 본 측정 이후 미사용 legacy harness 분기 제거 후 1명 smoke 재실행(24.30초/4회 모델/오류 0). 중간 wrapper 초기화 오류는 수정했고 최종 smoke에 포함되지 않는다.
- `verify.py`: 집계 모듈을 import하지 않는 endpoint sweep으로 모델 시간 검산, 원본 사용자/큐/Worker 시간과 집계 일치, Run/시도 대응, SQL/commit 호출 수, 공유 자원 수, 종료 검증.
- 홈 경로만 치환한 gzip 원본을 저장하고 원본 SHA-256·변환 범위·종료 기록 보존. 아카이브로 다시 집계한 결과가 최초 집계와 byte-for-byte 일치했다.
- 보고서 artifact 검증·HTML 패키징·구조/원본 일치 검증 통과. 설치된 호환 Chromium 부재로 실제 브라우저 시각 검증은 미수행. 새 브라우저는 설치하지 않았다.
- 운영 코드를 변경하지 않아 기존 전체 회귀 테스트는 반복하지 않았다. 계측 도구 문법·정리 후 실동작·수치 검산을 수행했다.
- 전용 임시 PostgreSQL `dtest-latency-profile-test`와 해당 임시 볼륨 정리 완료. 기존 앱/DB/Locust 컨테이너는 변경하지 않았다.

## 한계

각 조건 1회, 동시에 시작하는 배치이며 지속 유입/운영 SLA 검증이 아니다. 실제 DB RTT·여러 Pod·PV·LLM 제한·Executor 제출/이벤트·취소/실패는 제외했다. 진단 계측 오버헤드가 포함되고 checkpoint 비용은 다른 구간과 겹치지 않는 관측 시간만 집계했다. 최종 수신 시간은 클라이언트 perf_counter 경계를 복원하므로 작은 함수 호출 경계 오차가 있다. HTTP middleware 시간은 헤더 응답까지이며 SSE 전체 연결 시간이 아니다.

원격 push·운영 배포·현재 028 브랜치의 베이스 병합은 수행하지 않았다.
