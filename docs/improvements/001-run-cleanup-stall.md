# 001. 취소 감시 정리 중 Run 실행기 정체

| 항목 | 내용 |
|---|---|
| 상태 | 착수 전 |
| 시작일 / 완료일 | 미정 / 미완료 |
| 브랜치 | feature/runtime-hardening |
| 관련 commit | 미커밋 |
| 배포 상태 | 미배포 |

**문제와 영향**

Run의 그래프 처리 후 취소 감시 task를 정리하는 대기에서 멈춰, 순차 실행기가 다음 Run을 가져오지 못하는 현상이 관측됐다. Pod 전체가 종료된 상황과 다르며 HTTP와 heartbeat가 살아 있으면 정상 상태로 오인할 수 있다. 실행 자리가 줄어 다른 사용자의 대기가 길어진다.

근거: [기존 정체 분석 보고서](../reports/run-delay-diagnosis-2026-09-28.md), [RunService](../../src/app/services/run_service.py), [재현 스크립트](../../scripts/diagnostics/reproduce_cancel_watcher_race.py).

**원인 판단**

- 확인된 사실: 실제 Run이 취소 감시 task 종료를 기다리는 정리 구간에 머문 현상을 관측했다.
- 기존 재현 결과와 라이브러리 소스는 취소 경합 가설을 뒷받침한다.
- 실제 실행 당시 라이브러리 내부에서 취소가 소실되는 정확한 순간까지 직접 관측한 것은 아니다. 라이브러리 버전 교체만으로 해결됐다고 단정하지 않는다.

**개선 방향과 범위 — 논의안**

- 정상 종료용 stop 신호와 사용자 업무 취소를 구분한다.
- 취소 감시·heartbeat·token flush 등 종료 경로의 무기한 대기를 없애는 방법을 검토한다.
- 실행 단계와 기한을 구분해 heartbeat만 살아 있는 정체를 감지한다.
- 기한이 지났다는 이유로 살아 있는 graph를 버리고 실행 자리·세션 소유권을 재사용하지 않는다. 종료 확인 또는 격리·복구 정책을 마련한다.
- 동시 슬롯 확대·SSE 전환·배포 구조 변경은 이 항목에서 자동으로 포함하지 않는다. 필요한 최소 수정 범위는 구현 전 확정한다.

**완료 조건**

- 정상 완료·사용자 취소·실행 오류·종료 경쟁에서 정리가 완료되거나 명시적인 복구 대상으로 전환된다.
- 실행 task가 남은 상태에서 다음 실행이 같은 소유권을 재사용하지 않는다.
- 정체가 숨은 채 실행 용량이 영구 소실되지 않는다.
- 기존 재현 및 변경에 필요한 회귀 검증 결과를 기록한다.

**실제 작업 결과**

미구현. 현재 문서는 기존 분석과 개선 방향만 기록한다.

**검증 결과**

이번 항목의 새 검증은 미실행. 이전 분석 보고서의 시험을 이번 수정의 통과 결과로 재사용하지 않는다.

**영향·복구·후속 작업**

구현 후 변경 파일, 호환성, 되돌리는 방법, 남은 제한과 실제 배포 여부를 기록한다.
