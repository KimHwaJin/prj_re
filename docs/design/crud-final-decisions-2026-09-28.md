# CRUD 최종 결정과 프로젝트 공유 컨텍스트

> 2026-10-01 사용자 식별 변경: 아래 `X-User-Id` 계약은 이전 결정 기록이다. 현재 서비스는 SSO 로그인 쿠키와 변경 요청의 `X-CSRF-Token`을 사용하며, [현재 SSO 계약](../sso-authentication.md)을 우선한다. Run/계획/데이터 body와 내부 UUID 소유권은 유지한다. Gaia body의 user_id를 검증된 로그인 신원으로 신뢰하지 않는다.

2026-09-28 · 사용자 항목별 확정사항과 추가 요구사항. 설계 기록이며 구현·마이그레이션·배포 완료가 아니다. 이전 CRUD 보고서의 권장안과 충돌할 때 이 문서의 사용자 결정이 우선한다.

## 확정한 범위

| 항목 | 결정 |
|---|---|
| 사용자 식별 | 사용자용 API는 X-User-Id 공통 헤더. 비밀번호·로그인·토큰 발급 없음. 활성 사용자와 DB role/소유권 검사. |
| 사용자 등록·수정·삭제 | 관리자 전용. 등록 시 role을 admin/user 중 선택 가능. |
| 공개 사용자 ID | 사람이 입력할 수 있는 문자열 ID. 내부 UUID와 기존 FK는 유지하고 문자열 식별자를 매핑. |
| 사용자 삭제 | 미종료 작업이 있으면 거절. 종료 후 사용자와 소유 프로젝트·세션·메시지를 함께 soft delete. |
| 세션·프로젝트 삭제/이동 | 실행 중 세션 이동·삭제, 미종료 작업이 있는 프로젝트 삭제는 거절. 이름 변경은 실행 문맥과 분리. |
| 기본 프로젝트 | DELETE 거절. 전체 대화 비우기를 필수 신규 기능으로 만들지 않음. |
| 단건 조회 | 응답에서 버리는 전체 하위 메시지/세션 조회·집계 제거. 하위 목록은 페이지 API 사용. |
| 메시지 공개 API | GET 유지, POST/PATCH/DELETE는 공개 API에서 제외. 내부 메시지 저장 기능 유지. |
| 공개 실행 API | Runs 중심. 공개 run_id는 최초 접수→HITL→Executor 최종 완료까지 동일하게 유지. |
| Tasks API | 필요한 조회/resume/cancel/stream 기능을 Runs로 이관 후 제거. 내부 Task 상태/테이블은 기능 보존·이전 비용을 검토해 유지 또는 통합. |
| 프로젝트 system_prompt | 유지. 값이 있으면 해당 프로젝트의 Agent 실행에서 매번 함께 적용. |
| project_memory | 프로젝트 단위로 별도 영속 관리. Agent가 갱신하고 같은 프로젝트의 다른 세션 실행에서 프롬프트 컨텍스트로 공유. |
| 불필요한 요청 설정 | 사용처 없는 Session 자유 settings, Message llm_max_retries 등은 공개 계약에서 제외. Project system_prompt와 공유 메모리는 제외 대상 아님. |
| LLM 선택 | main_model_name 생략 시 기본 모델, 지정 시 등록된 모델. 동일 공개 Run의 resume에서는 선택 유지. |
| 템플릿 승격 | 일반 사용자와 관리자 모두 가능. Executor 실행 성공은 필수 조건이 아님. 관리자 승인·실행 성공 대기를 추가하지 않음. |

메시지 편집/분기·과거 대화 import·사용자별 메시지 숨김 같은 신규 제품 기능은 현재 범위에 추가하지 않는다. 데이터 저장 자체가 불필요하다는 뜻은 아니며, Runs 접수와 내부 실행이 사용자/Agent 메시지 저장을 담당한다.

## 사용자 등록의 role

```http
POST /api/v1/users
X-User-Id: admin-001
Content-Type: application/json

{
  "user_id": "user-001",
  "user_name": "홍길동",
  "role": "user"
}
```

role은 admin/user enum으로 검증한다. 관리자는 role=admin으로 다른 관리자도 등록할 수 있다. 생략 시 기본값 user를 권장한다. 호출자 권한은 X-User-Id의 기존 DB 역할로 검사하고, body의 role은 생성할 대상 사용자의 속성으로 처리한다. 같은 필드가 호출자 권한을 부여하지 않는다.

사용자 수정에도 관리자 권한으로 role 변경을 허용하되 마지막 활성 관리자 삭제/강등을 보호한다. /users/me와 사용자 조회 응답에도 role을 포함한다. 사용자와 기본 Project는 같은 transaction으로 생성한다. 최초 관리자는 멱등 배포 초기화로 생성한다.

현재 UserCreate/UserUpdate에는 user_name만 있고 UserModel에는 admin/user 역할이 없으므로 실제 스키마·모델·마이그레이션 변경이 필요하다. 프로젝트의 OWNER/EDITOR/VIEWER 멤버 역할과 서비스의 admin/user 역할은 구분한다.

## 공개 Run과 내부 실행 구간

```text
public run_id = R (전체 플로우에서 유지)
  최초 실행 구간
    → 사용자 승인 대기
  resume 실행 구간
    → 다음 승인 대기
  resume 실행 구간
    → Executor 제출·장기 대기
  Executor 이벤트 이후 실행 구간
    → 최종 완료
```

실행 구간마다 내부 ID/attempt/lease/event 기록은 둘 수 있다. 프론트가 resume마다 새 공개 ID로 갈아타거나 별도 Task ID를 알아야 하는 계약은 제거한다. 명령별 Idempotency-Key는 최초 접수·각 resume에서 구분하고 동일 명령의 재시도에는 같은 키를 사용한다.

공개 Run ID를 하나로 통일하는 것이 DB 모든 실행 행을 하나로 합치거나 checkpoint의 thread_id를 즉시 바꾼다는 뜻은 아니다. 기존 Run/Task/checkpoint/Executor binding을 연결하는 이전 계획이 필요하다. 같은 세션 잠금은 공개 API 종류와 무관하게 유지한다.

## 프로젝트 system_prompt와 project_memory

두 데이터는 수명과 작성 주체가 다르므로 별도로 관리한다.

| 구분 | system_prompt | project_memory |
|---|---|---|
| 목적 | 프로젝트에 적용할 사용자 지정 지침 | 프로젝트 내 다른 세션에서도 재사용할 업무 정보·기억 |
| 작성 주체 | 프로젝트 수정 권한이 있는 사용자 | Agent 내부의 메모리 관리 기능 |
| 범위 | 프로젝트 | 프로젝트 |
| 실행 중 사용 | Agent 고정 프롬프트에 함께 추가 | 별도 공유 컨텍스트로 함께 제공 |
| 변경 기록 | prompt_version | 독립 memory_version/갱신 출처 |

Agent마다 이 기능을 새로 구현하지 않도록 공통 실행 컨텍스트에 project_id, system_prompt, prompt_version, project_memory, memory_version을 전달한다. 공통 프롬프트 조립 경계에서 이를 적용한다. Agent의 고정 역할 프롬프트를 교체하거나 공유 메모리를 system_prompt 문자열에 덮어쓰는 방식으로 구현하지 않는다.

```text
Agent 고정 프롬프트
  + Project.system_prompt (있을 때)
  + Project.project_memory (있을 때)
  + 해당 세션/Run의 입력과 대화 문맥
```

공유 메모리와 LangGraph checkpoint는 구별한다. checkpoint는 해당 실행/세션의 재개 상태이며 프로젝트 메모리는 여러 세션이 공유하는 영속 컨텍스트다. 프로세스 메모리에만 저장하거나 한 세션 checkpoint에만 넣어 다른 세션도 보일 것이라고 가정하지 않는다. 기존 PostgreSQL을 활용하며 별도 메모리 서비스 도입을 전제로 하지 않는다.

### 구현 설계에 적용할 기본 방향

아래 세부 동작은 사용자 요구를 만족시키기 위한 구현 권장안이다.

1. 최초 실행과 각 resume 실행 구간 진입 시 프로젝트 컨텍스트를 읽고 실제 사용한 버전을 기록한다. 한 구간 안에서는 같은 snapshot을 프롬프트 조립에 재사용해 LLM 호출마다 불필요한 DB 조회를 반복하지 않는다. 긴 Executor 대기 동안 connection/transaction을 유지하지 않는다.
2. 공통 LLM 호출 경계에서 프로젝트 지침·메모리가 빠지지 않게 적용한다. 같은 문자열을 메시지 이력에 계속 누적 저장하여 resume마다 중복 삽입하지 않는다.
3. 같은 프로젝트의 세션 A에서 Agent가 메모리를 영속 갱신하면, 이후 시작/재개하는 세션 B는 갱신된 버전을 읽는다. 이미 진행 중인 LLM 호출의 입력을 소급 변경하지 않는다.
4. 두 세션이 동시에 메모리를 수정할 때 이전 snapshot으로 전체 덮어쓰지 않는다. revision 비교와 충돌 시 재해석/병합 또는 변경분 반영으로 갱신 유실을 막는다. 이를 위해 프로젝트의 모든 Agent 실행을 통째로 직렬화하지 않는다.
5. 메모리 갱신에도 원본 Run/갱신 키를 기록해 Worker 재시도로 같은 메모리가 반복 추가되지 않게 한다. 출처와 버전을 남기고 크기·요약 정책을 적용한다. 다른 프로젝트의 내용이 섞이지 않도록 project_id를 강제한다.
6. Agent에 프롬프트로 메모리를 보여주는 것만으로 영속 갱신이 되는 것은 아니다. 공통 저장 port/tool을 통해 읽기·갱신 결과를 저장하고 Agent 개발 표준에 포함한다.

공개 메모리 편집 API는 사용자 요구가 없으므로 필수 기능으로 추가하지 않는다. Project system_prompt의 기존 관리 API는 유지한다. 공개 단건 조회에서 불필요하게 모든 세션/메시지를 읽지 않는 원칙도 유지한다.

## Workflow → Executor 변환과 승격 조건

사용자 설명에 따른 흐름은 다음과 같다.

```text
Workflow 문서
    → Agent가 해석
    → Executor API 규격의 요청으로 변환
    → Executor 제출
    → 실제 실행 결과
```

Workflow JSON 자체를 Executor에 그대로 제출한다고 가정하지 않는다. “변환 가능/변환 성공”, “제출 접수 성공”, “실제 실행 성공”은 서로 다른 사실이다. Run 성공 하나를 근거로 위 세 단계를 동일하게 취급하지 않는다.

**확정:** 승격 기능은 관리자에 한정하지 않고 일반 사용자도 사용할 수 있다. 다른 사용자의 비공개 후보를 임의로 변경할 권한까지 뜻하는 것으로 확대하지 않고 기존 소유권/가시성 계약을 따른다.

**최종 확정:** Executor 실행 성공 없이도 승격을 허용한다. Workflow 문서의 스키마/필수 구성과 접근 권한 등 자산 자체의 유효성은 검사하지만, 실제 실행 성공이나 그 성공을 대체하는 Run SUCCESS를 필수 승격 조건으로 두지 않는다. Executor 요청 변환·실제 제출을 승격의 필수 사전 단계로 새로 요구하지 않는다.

기존 WorkflowService.promote의 source_run.status == SUCCESS 조건은 현재 의미를 검토해 자산 유효성 기준으로 대체한다. 유효한 Workflow가 생성되었더라도 이후 Executor가 실패하면 원본 Run이 실패할 수 있기 때문이다. 원본 생성 이력/문서 버전은 추적용으로 보존한다.

템플릿 등록 상태와 실제 실행 검증 상태는 분리한다. 실행하지 않은 문서는 template이지만 실행 검증 완료는 아니다. 실행 이력을 제공할 때는 Workflow 버전/hash → Agent의 변환 요청 → execution_id/결과 연결로 해당 버전의 결과를 표시한다. 승격을 위해 이 실행 이력이 있어야 하는 것은 아니다.

## 확인할 동작

- 일반 사용자와 관리자 등록, 등록 role 기본값/허용값, 일반 사용자의 사용자 관리 거절, 마지막 관리자 보호.
- 미종료 Run이 있는 사용자 삭제 거절과 종료 후 소유 데이터 동시 숨김.
- 최초 요청/여러 HITL/Executor 대기·재개 이후에도 공개 run_id 유지, 내부 실행 구간 이력 보존.
- Project system_prompt가 최초 호출과 resume에서 실제 LLM 요청에 포함됨. 내용이 없는 경우 중복/빈 지침을 누적하지 않음.
- 프로젝트 A의 세션 간 메모리 공유, 다른 프로젝트와 격리, 동시 수정 충돌, 재시도 중복 갱신 방지.
- 모델을 서로 다르게 선택한 동시 Run에서 모델/프로젝트 컨텍스트가 섞이지 않음.
- 일반 사용자도 유효한 본인 후보를 실행 전 또는 Executor 실패 후 승격 가능. 승격만으로 실행 검증 완료로 표시하지 않음. 재시도 시 중복 template 생성 방지.
